## 0. 読み方と前提

本書は 4 つの層で構成する。層をまたぐ参照は ID で行う。

| 層 | ID 体系 | 定義箇所 | 対応 Issue |
| --- | --- | --- | --- |
| 開発者向け作業状態 | `W0-A` / `W0-B` / `W1`〜`W7` | §2 | #343 |
| 情報役割 | `R1`〜`R6` | §3.1 | #344 |
| 操作 | `OP-*` | §4.2 | #345 |
| 例外 | `E1`〜`E14` | §5.2 | #346 |

前提となる不変条件（本書は一切緩めない）:

1. 提案・差分・観測の採否は常に人間の明示操作であり、`decision_method:
   manual` として記録される（Principle 7）。自動化の対象は「調査・整理・
   再評価」までで、承認・適用は含まない。
2. 対象リポジトリのブランチ・実ファイルは自動では変更されない。差分生成は
   隔離 worktree 内に留まり、適用は開発者が行う（Principle 5 / 8）。
3. 推論が必要な判断にヒューリスティックのフォールバックを置かない。失敗は
   失敗として提示する（Principle 6）。
4. 本書の「自動化」は上記 1〜3 の内側だけで成立する（§4.1 の有限ゲート）。

## 2. 開発者向け状態モデル（Issue #343）

### 2.1 正準な作業状態

内部ステージ名（`understanding_initialized` 等）は開発者に露出しない。
開発者に見せるのは次の 8 状態のみ。

| ID | 表示名 | 開発者が達成すること（一文） |
| --- | --- | --- |
| `W0` | 開始できるか確認する（`W0-A` / `W0-B` の 2 変種。下表参照）| このリポジトリでインタビューを始められる状態にする |
| `W1` | システムが調べている | 待つ（操作は不要） |
| `W2` | 理解の要点を確認する | AI が読み取ったシステム理解が今回の対象として正しいか判断する |
| `W3` | 判断が必要な質問に答える | コードから確定できない意図・制約・優先順位を答える |
| `W4` | 意図とのズレを確認する | 自分の意図と現在の理解の食い違いを 1 件ずつ確定する |
| `W5` | 提案を承認する | どの計測提案を採用するか決める |
| `W6` | 差分を確認する | 生成された差分が意図どおりか確認する |
| `W7` | 結果と残りを確認する | 適用・接続へ進む、または未解決事項を引き継いで終える |

`W0` は 2 つの変種に分かれる。前提が未達の状態と開始可能な状態では、
開発者が行える操作が異なるため、同一状態にまとめると「実行できない主操作を
表示する」ことになり原則 P1 / P3 に反する。

| ID | 表示名 | 開発者が達成すること（一文） |
| --- | --- | --- |
| `W0-A` | 開始の前提を満たす | 対象リポジトリの snapshot を用意する |
| `W0-B` | インタビューを始める | このリポジトリでインタビューを開始する |

`W1` を除く全状態は「開発者の判断」を求める状態であり、`W1` だけが
「システムの処理」を待つ状態である。この対比が状態モデルの骨格である。

### 2.2 状態決定（2 段階評価、決定的）

表示状態は **2 段階** で決まる。第 1 段は first-match のルール表で候補状態を
求め、第 2 段は「完了済み状態への後退には明示確認が要る」という §2.5 基準 C を
適用する。ルール表だけでは基準 C を実現できない（回答修正で未回答質問が
発生した瞬間、ルール表は無条件に `W3` を選んでしまう）ため、第 2 段が必要になる。
両段とも永続化された事実だけを入力とし、同じ事実からは常に同じ状態が決まる。

#### 進捗順序（第 2 段の比較対象）

第 2 段で「手前 / 以降」を比較できるのは、**開発者の判断が進む順序を持つ
状態だけ** である。

```text
進捗順序:  W2 < W3 < W4 < W5 < W6 < W7
順序を持たない状態:  W0-A, W0-B, W1
```

`W0-A`（前提未達）と `W1`（システム処理中）は、ワークフロー上の位置ではなく
**一時的な事情** を表す状態なので、進捗順序を持たない。したがって:

- 候補が `W0-A` / `W0-B` / `W1` のときは、第 2 段の抑止を **適用しない**
  （そのまま表示する）。
- これらの状態は `reached_state` を更新しない（前進も後退もさせない）。

この扱いが無いと、正常系の `W3` → `W1`（回答の自動反映）や `W5` → `W1`
（差分生成）でさえ「`reached_state` より手前への後退」と判定され、システム
処理中であることが表示されなくなる。

#### 第 1 段: 候補状態のルール表（first-match）

一致は排他ではなく順序で解決する（`#287` の Alignment 分類ルール表と同じ
first-match 方式）。**未解消のブロッキング失敗** の行は、それが妨げている状態の
行の直前に置く（そうすることで、失敗が起きても「もっと手前でできる作業」が
あればそちらが優先される）。

| 順 | 条件 | 候補状態 |
| --- | --- | --- |
| 1 | snapshot が存在しない（`E1`）| `W0-A` |
| 2 | セッションが 1 件も選択されていない | `W0-B` |
| 3 | セッションが明示的に終了済み（既存の `status = closed`。中断 / 引き継ぎを含む）| `W7` |
| 4 | このセッションに紐づく処理の **実行中レコード** がある（§2.3 `W1`）| `W1` |
| 5 | 未解消のブロッキング失敗があり、その対象状態が `W2`（`E3-a`）| `W2` |
| 6 | 未確認の理解がある（理解に内容があり、確認が未完了、または Capability 構成の再確認が必要）| `W2` |
| 7 | 未回答の必須質問がある（提示中の質問、未回答の高優先度 Q&A、ゼロベース質問の未完のいずれか）| `W3` |
| 8 | 未解消のブロッキング失敗があり、その対象状態が `W4`（`E4-a`）| `W4` |
| 9 | 未対応の Alignment 項目がある（要確認 + 一括レビュー可の未対応件数 > 0）| `W4` |
| 10 | 未解消のブロッキング失敗があり、その対象状態が `W5`（`E12` 生成失敗）| `W5` |
| 11 | 未レビューの提案がある / 提案が未生成で生成可能である / **承認済み提案が 1 件以上あり、現在の承認セットに対応する差分が存在しない** | `W5` |
| 12 | **現在の承認セットに対応する差分が存在し**、その差分に対する差分レビューが未完了である | `W6` |
| 13 | 上記いずれにも該当しない | `W7` |

補足:

- **明示的な終端の行**（3）: ブロッキング失敗から「中断 / 引き継ぎ」を選ぶ操作は、
  既存のセッション `status` を `closed` にし、`decision_method: manual` の監査記録を
  残す（`OP-D14`）。行 3 は実行中・失敗行より先に評価するため、未解消の失敗を
  人間のゲートを飛ばして解消扱いにせず、表示だけを安全に `W7` へ移せる。この
  `W7` は進捗到達を表さないため `reached_state` を更新しない。再開時は `status` を
  `open` に戻し、未解消の失敗を含む通常のルールを再評価する。
- **ブロッキング失敗の行**（5 / 8 / 10）: 実行中レコードが失敗で終了すると行 4 に
  該当しなくなるため、失敗の表示先が決まらなくなる。これを防ぐため、失敗
  レコードは **対象状態**（その失敗が妨げている状態。`W2` / `W4` / `W5` の
  有限集合）を持ち、未解消の間だけ該当行に一致する。「未解消」とは、同種の
  処理がその後成功しておらず、かつ前提（`E2` など）が解消していないことを指す。
  失敗レコードが解消すると行は一致しなくなり、通常の行に戻る。
- 行 5 が行 7 より上、行 8 が行 9 より上、というように失敗行を対象状態の
  直前に置いているため、たとえば「差分生成に失敗したが未対応の Alignment 項目も
  ある」場合は先に `W4` が選ばれる。開発者がまだできる作業を、失敗表示で
  塞がない。
- 行 9 が行 11 より上にあるのは、意図とのズレが未確定のまま提案を承認すると
  承認の前提が崩れるため。`W5`/`W6` 到達後に新しく発生したズレの扱いは
  第 2 段が決める。
- 行 4 の「実行中」は、対象セッションに紐づく処理だけを見る。他 System /
  他セッションの処理は `W1` を発生させない。クライアントの通信中フラグは
  入力にしない（§2.3 `W1`、§8.1 の実装前提 B）。
- 行 11 の 3 つ目の条件が **承認済み提案と差分の対応関係** を見るのは、全提案を
  承認し終えた直後や差分生成に失敗した直後に `W5` から落ちてしまうのを防ぐ
  ため。「現在の承認セットに対応する差分」は、差分の生成時刻が提案の承認・
  編集・却下の最終更新時刻より後であることで決定的に判定できる（新しい永続
  事実を必要としない）。対応しなくなった差分は行 12 にも一致しない
  （差分レビューの完了記録は、それが対象とした差分に紐づく。§8.1 の実装前提 A）。
- 行 1 の `E1` 以外の前提未達（Repository HEAD のズレ `E2`）は `W0-A` を
  発生させない（§5.2 参照）。

#### 第 2 段: 後退の抑止（明示確認）

セッションには、進捗順序上で現在到達している判断状態 `reached_state` を永続化
する。通常の前進遷移では候補状態へ進み、明示的な戻りを承諾したときだけ手前へ
移る **現在のワークフローチェックポイント** であり、過去に到達した最大状態を
表す単調値ではない。順序を持たない状態では更新しない。

0. 第 1 段の行 3（明示的な終端）に一致した場合、`W7` を表示するが
   `reached_state` は更新せず終了する。中断・引き継ぎは進捗到達ではないためである。
1. 候補状態が進捗順序を持たない（`W0-A` / `W0-B` / `W1`）場合、抑止を適用せず
   そのまま表示して終了する。
2. 候補状態が `reached_state` **以降** であれば、候補状態をそのまま表示する
   （`reached_state` も候補状態へ更新する）。
3. 候補状態が `reached_state` より **手前** の場合、その後退を引き起こした
   事実（回答の修正、Intent の変更、Capability 構成の変更、snapshot 更新に
   よる再レビュー、ブロッキング失敗の発生等の記録）を **戻り要求** として
   識別する。未承諾の戻り要求が 1 件以上ある間、**表示状態は `reached_state`
   のまま** とし、現在地に `E8`（確認待ちの戻り）を 1 操作の導線として提示する。
4. 開発者が「先に確認する」を押すと、その戻り要求に対する **承諾** が永続化
   される。以後の評価では候補状態がそのまま表示状態になり、`reached_state` も
   候補状態まで引き下げる。承諾は開発者の判断なので `decision_method: manual`
   として記録する（§8.1 の実装前提 D）。
5. 承諾は戻り要求ごとに記録する。承諾後に新しい戻り要求が発生した場合は、
   改めて 3. からやり直す（過去の承諾は再利用しない）。

抑止中にブロッキング失敗が候補になっている場合（例: `reached_state` が `W5` で、
回答修正後の理解再構築に失敗して候補が `W2`）、その失敗は `reached_state` の
主作業を妨げていないので、`R5` の失敗表示を現在地に添えるだけで主作業は
継続できる。「妨げている状態」は候補状態の側であり、そこへ移るには承諾が要る。

この 2 段構成により、後退は必ず開発者の明示操作を経由し、かつ表示状態は
再読込後も同じ事実から復元できる（原則 P9）。抑止中も `reached_state` の
主作業は通常どおり操作できる。「戻りを承諾するまで何もできない」状態は作らない。

### 2.3 状態ごとの目的・開始条件・完了条件・遷移

#### W0-A 開始の前提を満たす

- 目的: 対象リポジトリの snapshot を用意する。
- 開始条件: 最新 snapshot が存在しない（`E1`）。
- 完了条件: snapshot が 1 件以上存在する。
- 次状態: `W0-B`。自動。
- 戻り: なし（最初の状態）。
- 表示すべき情報: 何が無いか、それをどこで満たすか（Repository 画面）、
  満たしたあと何が起きるか。
- 注意: この状態では「インタビューを開始」を表示しない。実行できない操作を
  disabled で見せない（原則 P3）。主操作は Repository 画面への導線 1 つ。

#### W0-B インタビューを始める

- 目的: このリポジトリでインタビューを開始する。
- 開始条件: snapshot が存在し、セッションが 1 件も選択されていない。
- 完了条件: セッションが 1 件作成・選択されている。
- 次状態: `W1`（セッション作成と同時にシステムが調査を開始する。自動）。
- 戻り: なし。
- 表示すべき情報: 対象 snapshot、開始したあとに何が起きるか。

#### W1 システムが調べている

- 目的: 開発者を待たせている理由と、待ち終わったら何が求められるかを示す。
- 開始条件: 対象セッションに紐づく処理の **実行中レコードが永続化されている**。
  クライアントの通信中フラグ（`isPending`）は開始条件にしない — それに依存
  すると再読込で `W1` が消え、§2.6 の原則 P9 を満たせない。したがって
  「`W1` を発生させうる処理は、実行中であることを永続事実として持つ」ことが
  実装前提になる（§8.1 の実装前提 B）。実行中レコードを持たない処理は
  `W1` を発生させず、進行中表示は現在地の一時的な補助表示に留める。
- 完了条件: 実行中レコードが全て終了状態（成功・失敗いずれも）になった。
- 次状態: いずれの場合も §2.2 を再評価する。**失敗しても `W1` に留まらない** —
  実行中レコードが終了した時点で行 4 に一致しなくなるため。ブロッキング失敗は
  §2.2 第 1 段の失敗行（5 / 8 / 10）でその対象状態が選ばれ、そこに復旧操作を
  出す。劣化失敗は通常の行で決まる状態へ進み、劣化表示を添える。
- 戻り: なし。
- 表示すべき情報: 実行中の処理名（開発者語で 1 行）、対象、完了後に求められる
  こと。進捗率・内部ステージ名は出さない。

#### W2 理解の要点を確認する

- 目的: AI が構築したシステム理解が「今回のセッションの対象」として妥当かを
  開発者が判断する。
- 開始条件: 理解に内容があり、確認が未完了、または Capability 構成の再確認が
  必要（`#312` のカスケード）。
- 完了条件: 開発者が理解を確認済みにした（`decision_method: manual` の確定
  記録）、または訂正を送信して再構築が走った。
- 次状態: `W3`（未回答質問がある場合）/ `W4` / `W5`。§2.2 で決まる。自動。
- 戻り: `W3`〜`W7` から、回答修正・前提変更で理解が再構築されたとき。明示確認。
- 例外: 理解の構築・更新に失敗し、かつ質問による代替経路も提示できない場合
  （`E3-a`）はこの状態がブロッキング表示になる（§2.2 第 1 段 行 5）。主作業
  カードの中身が復旧カード（失敗内容 + 再試行）に置き換わる。
- 表示すべき情報: 要点（目的・主要機能）と、その根拠。全文の理解ツリーは
  既定で開かない（`R4`）。

#### W3 判断が必要な質問に答える

- 目的: コード・Runtime から確定できない事項だけを開発者が答える。
- 開始条件: 未回答の必須質問がある。
- 完了条件: 必須質問が全て「回答済み / 引き継ぎ済み / 保留（明示）」のいずれか
  になった。「未回答のまま放置」は完了条件を満たさない。
- 次状態: `W4` / `W5`。回答バッチ後は先に `W1`（自動更新）を経由する。自動。
- 戻り: 回答を修正したとき `W3` に留まる。理解の再構築が伴う場合は `W1` →
  `W2` へ明示確認付きで戻る。
- 表示すべき情報: 現在の 1 問、仮説、根拠、回答選択肢、「わからない」の入口。
  質問一覧は既定で開かない（`R4`）。

#### W4 意図とのズレを確認する

- 目的: 開発者の意図（Intent Brief）と現在の理解の食い違いを 1 件ずつ確定する。
- 開始条件: 未対応の Alignment 項目（要確認 / 一括レビュー可）が 1 件以上ある。
- 完了条件: 未対応件数が 0 になった。確認不要 / 参考情報 / 変更なしの項目は
  完了条件に影響しない。
- 次状態: `W5`。自動。
- 戻り: 回答修正・Intent 変更・前提変更で新しい未対応項目が発生したとき。
  `W5`/`W6` からの戻りは明示確認。
- 例外: 突き合わせの初回 build に失敗し、有効な Alignment 項目が 1 件も無い
  場合（`E4-a`）はこの状態がブロッキング表示になる（§2.2 第 1 段 行 8）。
  復旧操作は再試行のみで、**「突き合わせを行わずに進む」という迂回は用意
  しない** — それは Alignment 確認という人間のゲート（§8.2）を無効化する
  新しい判断になってしまう。再試行で解消しない場合は §5.3-6 に従い、`W7` の
  中断または引き継ぎ終端へ安全に抜ける。
- 表示すべき情報: 項目の主張、根拠（`#295` の先出し条件に該当する場合は初期
  展開）、5 分類の件数サマリ。監査詳細は `R6`。

#### W5 提案を承認する

- 目的: 生成された計測提案（メタデータ + プローブ計画）の採否を決める。
- 開始条件: 次のいずれか（§2.2 第 1 段 行 11）。
  - 未レビューの提案がある
  - 提案が未生成で生成可能である
  - 承認済み提案が 1 件以上あり、現在の承認セットに対応する差分が存在しない
    （全提案を承認し終えた直後、差分生成に失敗した直後、既存差分より後に
    承認・編集・却下が行われた場合を含む）
- 完了条件: 未レビュー提案が 0 件、かつ次のいずれか。
  - 承認済み ≥ 1 件で、その承認セットに対応する差分が生成済みである
  - 承認済み 0 件（全却下）である
- 次状態: 承認済み ≥ 1 件 → システムが差分を生成（実行中は `W1`）。成功で
  `W6`、失敗は §2.2 第 1 段 行 10 により `W5` が選ばれ `E12`（ブロッキング）を
  表示する。承認済み 0 件（全却下）→ `W7`（中断の終端）。
- 戻り: snapshot 更新で `needs_review` に戻った提案が発生したとき。明示確認。
- 表示すべき情報: 1 提案あたり、対象シンボル、Capability、根拠、確信度、
  提案の来歴（decision method / model / mock 表示）。差分の生成に失敗した
  場合は、失敗内容と再試行を同じ場所に出す（§4.4）。

#### W6 差分を確認する

- 目的: 生成された差分が意図どおりで、適用してよい内容かを開発者が確認する。
- 開始条件: 差分が存在し、**その差分に対する** 差分レビューが未完了。差分が
  存在しない間はこの状態にならない（§2.2 第 1 段 行 12）。差分レビューの完了
  記録は対象の差分に紐づくため、新しい差分が生成されると前の完了記録は
  引き継がれない。
- 完了条件: 開発者が「この差分を確認した」ことを明示記録した（§8.1 の実装前提
  A）。**この記録は主操作そのものであり、ダウンロード・差分表示・適用手順の
  閲覧では代替されない** — それらは確認を助ける補助操作であって、確認した
  という判断の記録ではない（§4.3 の主操作と完了条件は同一の操作を指す）。
- 次状態: `W7`。自動。
- 戻り: 提案を追加承認・再レビューした場合、差分は再生成対象になり `W5` →
  `W6` を再度通る。明示確認。
- 表示すべき情報: 差分本体、この差分のベース commit、スキップされた対象と
  理由、適用が開発者の責任であること。

#### W7 結果と残りを確認する

- 目的: 適用と接続確認へ進む、あるいは未解決事項を残したまま安全に終える。
- 開始条件: ルール表の他の行に一致しない。
- 完了条件: なし（終端状態）。§5.4 の 3 終端のいずれかとして表示する。
- 次状態: 新しい判断材料（回答修正・前提変更・新規観測提案・再レビュー）が
  発生したとき、明示確認で該当状態へ戻る。
- 表示すべき情報: 何が完了したか、未解決事項（引き継ぎ待ち・保留・却下）、
  次の作業（接続セットアップガイド）。履歴・監査・評価指標への入口。

### 2.5 自動遷移と明示確認の判断基準

遷移は次の 4 基準のいずれかに必ず該当する。基準は有限で、どの遷移がどれに
該当するかは §2.3 に記載済み。

| 基準 | 内容 | 遷移例 |
| --- | --- | --- |
| A | システム処理の開始・完了による遷移は **自動** | `W0-B`→`W1`, `W1`→`W2` |
| B | 開発者の確定操作によって完了条件が満たされた場合、次状態へ **自動** で進む | `W2`→`W3`, `W3`→`W4`, `W4`→`W5`, `W5`→`W6`, `W6`→`W7` |
| C | 既に完了した状態へ戻る遷移は **明示確認**。§2.2 第 2 段の戻り抑止により、承諾が永続化されるまで表示状態は `reached_state` のまま | `W5`→`W2`（前提変更）, `W6`→`W5`（再レビュー）, `W7`→`W4`（新規ズレ）|
| D | 順序を持たない状態（`W0-A`）へのブロッキング中断は **自動**。進捗順序内のブロッキング失敗は候補状態として扱われ、第 2 段の抑止に従う。劣化例外は遷移を起こさない | `*`→`W0-A`+`E1`（自動）, `W5`→抑止→`W2`+`E3-a`（承諾が要る）|

基準 C の理由: 後退遷移は開発者が既に払った判断コストを巻き戻す。自動で
行うと「さっきまでやっていた作業が消えた」体験になり、`#342` が問題視する
「操作場所を探させる」状況を再生産する。1 操作の導線に留めることで、
「今の作業を終えてから戻る」判断を開発者が持てる。

基準 C は §2.2 第 2 段（戻り抑止）としてのみ実現できる。ルール表を単独で
評価すると、回答修正で未回答質問や未対応 Alignment 項目が発生した瞬間に
候補状態が `W3`/`W4` になり、明示確認を挟む余地が無くなる。抑止の状態
（`reached_state` と戻り要求ごとの承諾）は永続事実でなければならない —
クライアントだけに置くと再読込で抑止が消え、承諾していない後退が起きる。

### 2.6 セッション切り替え・再開時の状態

- 表示状態は §2.2 の 2 段階評価を **永続化された事実だけ** に対して再実行して
  決める（原則 P9）。再開時に特別な状態は存在しない。
- 状態判定に使ってはならないクライアント限定の事実（現行に存在するもの）:
  `manualMainTabState`, `lastMaterialization`, `lastEvidenceReadsState`,
  `answerRevisionReflectedState`（`interview.tsx:1538-1556`）、および各
  mutation の `isPending`。これらは再読込で失われるため、状態が読込前後で
  変わってしまう。
- 状態判定に使う永続事実のうち、現行に存在しないものは §8.1 に列挙する
  （A: 差分レビューの完了、B: 実行中 / 失敗レコード、C: `reached_state` と
  戻り要求、D: 戻り要求への承諾）。
- 「途中まで入力した自由文」「開いていた詳細」の復元は行わない（保存する価値
  より、復元漏れによる不整合の害が大きい）。ただし **送信済みの回答・確定・
  承認は必ず永続化された事実として復元される**（`#288` の「回答は refresh
  失敗を越えて残る」方針と同じ）。
- セッションを切り替えたとき、前セッションの表示状態・選択・展開状態は
  一切引き継がない。

### 3.1 情報役割の定義

| ID | 役割 | 表示規則 |
| --- | --- | --- |
| `R1` | 常に必要な現在地 | 全状態で常時表示。1 画面に 1 箇所のみ |
| `R2` | 現在の必須作業 | 現在状態でのみ表示。視覚的に最優先。主操作を内包する |
| `R3` | 判断に必要な根拠 | 現在状態で既定表示。ただし §3.4 の分量規則に従う |
| `R4` | 必要時に開く詳細 | 既定は折りたたみ。開くのは開発者の操作 |

役割の割当規則:

- **役割は 1 要素 1 つに限る。** 状態によって役割が変わる要素があってはならない
  （実装時にマトリクスを一意に解釈できなくなる）。1 つの UI 表現が複数の役割を
  担っている場合は、要素の側を分割して各々に 1 役割を割り当てる（§3.2 の
  #51a / #51b がその例）。
- 「根拠でもあり履歴でもある」は許さない。迷った場合は、現在の判断に必要か
  否かで `R3` / `R6` を決める。
- `R5` は §5.1 の 3 区分のうち **ブロッキングと劣化** に対応する。**情報区分の
  例外（`E5` / `E6` / `E7` / `E8` / `E9` / `E13`）は `R5` ではない** — 通常
  フローの分岐なので、`R2` の主作業カードの中で扱う。
- 表記「`R2` 補助」は役割 `R2` の内側にある補助操作を指すものであり、別の役割
  ではない（§4.3 の補助操作に対応する）。

### 3.4 既定表示・必要時展開・非表示の判断基準

決定的な判定順（上から順に最初に一致したものを採用する）:

1. その要素が **現在の状態の主操作そのもの** → 既定表示（`R2`）。
2. その要素が **主操作の判断に必要** で、かつ主操作と同じ判断単位に属する
   → 既定表示（`R3`）。ただし §3.4.1 の分量上限を超える場合は、上限内の要約を
   既定表示し、残りを `R4` に落とす。
3. その要素が **現在ブロッキング中または劣化中の例外に属する** → 既定表示
   （`R5`）。例外が解消したら消す。
4. その要素が **同じ対象の全件・全履歴・監査情報** → 折りたたみ（`R4`/`R6`）。
5. その要素の **前提が未達** → 非表示。disabled にして説明文を添える形にしない
   （原則 P3）。
6. いずれにも該当しない → 非表示。

#### 3.4.1 根拠（`R3`）の分量上限

`R3` の既定表示は 1 状態あたり次を上限とする。上限は「開発者が判断を下すのに
必要な最小限」の目安であり、超過分は `R4` へ落とす。

- 主張・要約テキスト: 最大 3 件
- 根拠の位置参照（path:line）: 最大 3 件
- 件数サマリ: 分類ごとに 1 行（`#295` の 5 分類サマリはこの枠）

例外（既に `#295` で決定済みの先出し条件。本書はこれを変更しない）:
conflict / security・high_risk フラグ / runtime_check の mismatch・stale /
根拠が 1 件だけ、のいずれかに該当する項目は根拠を初期展開する。

### 4.1 自動化してよい処理の条件（有限ゲート）

次の 4 条件を **すべて** 満たす場合に限る。1 つでも欠ける場合は開発者の

| 条件 | 内容 |
| --- | --- |
| A1 | 対象リポジトリのブランチ・実ファイルを変更しない（隔離 worktree 内で完結する）|

承認しない）・`#288`（回答は refresh 失敗を越えて残る）を操作分類の判定基準へ

#### 4.2.1 `OP-S7`（差分生成）を自動側に置く根拠

差分生成は「承認された提案を隔離 worktree 上の patch として表現する」変換で
あり、A1〜A4 を満たす。人間のゲートは **その前（`OP-D9` の承認）** と
**その後（`OP-D10` の確認と、製品外での適用）** にあり、変換そのものはゲート
ではない。自動化することで次が同時に解消する:

- 「先に提案を承認してください」という前提説明（#34）が不要になる
- disabled な「差分を生成」ボタン（#33）が不要になる
- `W5` の完了と `W6` の開始が 1 つの事実（差分の存在）で決まる

Principle 5 / 8 との関係: 差分は隔離 worktree に留まり、対象リポジトリへの
commit / push / merge は一切行わない。この境界は変更しない。

#### 4.2.2 `OP-S8`（Runtime Reality Check）の自動実行条件

A1〜A4 は満たすが、LLM 実行コストを伴うため、無条件の自動実行はしない。
次の決定的条件を **すべて** 満たすときに 1 回だけ実行する:

1. 承認済み提案が 1 件以上ある
2. 前回のチェック以降に、対象コンポーネントの新しい Trace が存在する
3. 未回答の実態チェック質問が残っていない（現行の skip 条件と同じ）

条件が揃わない間はチェックの存在自体を画面に出さない（原則 P3）。生成された
確認質問は `W3` の質問として通常フローに合流し、そこから生まれる観測提案は
`W7` で人間が採否を決める（自動では観測を開始しない。現行方針を維持）。

### 4.3 状態ごとの主操作・補助操作

| 状態 | 主操作（1 つ） | 補助操作（現在の判断に直接必要なものだけ）|
| --- | --- | --- |
| `W0-A` | Repository で snapshot を作成する（画面遷移）| — |
| `W0-B` | インタビューを開始する | — |
| `W1` | （なし。§4.3.1）| 中断する |
| `W2` | この理解で進む | 訂正を入力する / まとめて修正する / Capability 構成を確定する |
| `W3` | 回答を送信する | わからない / 引き継ぐ / この質問を保留する / まとめて修正する |
| `W4` | この項目を確定する | まとめて回答する / 疑問を対話で解消する / 引き継ぐ |
| `W5` | この提案を承認する | 編集して承認する / 却下する |
| `W6` | **この差分を確認した**（確認の明示記録）| .patch をダウンロードする / 差分を別画面で開く / 適用手順を見る |
| `W7` | 終端ごとに 1 つ（§5.4）| 新規観測提案を採否する / 履歴と監査情報を見る |

規則:

- 主操作は現在地（`R1`）が示す「次にやること」と **同一の操作** であり、
  同じカード内に置く。別タブ・別パネルに置かない（原則 P2）。
- **主操作は、その状態の完了条件を満たす操作そのものでなければならない。**
  `W6` の主操作が「.patch をダウンロード」ではなく「この差分を確認した」で
  あるのはこのため — ダウンロードは差分を読むための手段であって「読んで
  問題ないと判断した」ことの記録ではなく、ダウンロードを完了扱いにすると
  内容を見ないまま `W7` へ進めてしまう。ダウンロード・差分表示・適用手順は
  すべて補助操作に置く。
- 補助操作は主操作と同じカード内、主操作より低い視覚優先度に置く。
- 補助操作が 4 つを超える状態は、情報設計の誤りとみなして再分割する。
- 自動処理の通常実行ボタン（`OP-S1`〜`OP-S8`）は主操作にも補助操作にも
  現れない。これらは `R5` としてのみ、対応する例外の表示の中に出る。

#### 4.3.1 `W1` が主操作を持たない理由

`W1` は唯一「システムの処理を待つ」状態であり、開発者が進行のために行える
操作が存在しない。ここに操作を置くと、それは必ず「不要な手動起動」か
「中断」のどちらかになる。前者は #342 の根本原因 3 そのものなので置かない。
したがって `W1` の主操作は定義せず、補助操作として「中断」だけを置く。

これは P1（1 状態 1 主作業）の唯一の例外であり、他の状態へ拡張しない。

### 4.4 自動処理の開始・完了・失敗時の表示方針

| 局面 | 表示 | 置き場所 |
| --- | --- | --- |
| 開始 | 実行中の処理名（開発者語で 1 行）と対象。進捗率・内部ステージ名・ジョブ ID は出さない | 現在地（`R1`）の更新状況 |
| 完了 | 結果を主作業へ反映する。完了そのものの通知は出さない（状態の変化が通知である）| — |
| 失敗（ブロッキング）| 何が失敗したか / 主作業への影響 / 再試行操作 / 通常フローへ戻る条件 の 4 点を **同じ枠内** に出す | 現在地の直下（`R5`）|
| 失敗（劣化）| 影響範囲（どの補助情報が欠けるか）と、主作業は継続できる旨 | 該当する補助情報の位置（`R5`）|
| 失敗の履歴 | 現在の主作業をブロックしていない過去のエラーは主フローに出さない | 履歴と監査情報（`R6`）|

- 再試行は「同じ処理をもう一度」に限り、代替のヒューリスティック実行を
  提示しない（Principle 6）。
- 同一処理の連続失敗を回数で表示しない（回数は判断材料にならない）。
  代わりに「何が足りないか」を書く。

### 4.5 開発者へ質問してよい条件

質問を開発者に提示できるのは、次の 4 条件を **すべて** 満たす場合に限る。

| 条件 | 内容 |
| --- | --- |
| Q1 | 質問の内容が、意図 / 優先順位 / 制約 / 業務事情 / 複数の正解がある設計判断 / 承認 のいずれかである（Question Router の `human_only` または `hybrid`）|
| Q2 | `system_researchable` を含む場合は、先に調査を実行済みで、なお確定できない部分だけを聞いている（`hybrid` の `decision_question` がこれにあたる）|
| Q3 | 同じ趣旨の未解決質問が既に提示されていない |
| Q4 | 回答可能領域（`#291`）に含まれる。含まれない場合は、担当外である旨と引き継ぎ導線を必ず添えて提示する（隠さない）|

Q2 の帰結として、**コードや Runtime から調べられる事実を先に開発者へ質問
してはならない**。調査を経ずに提示された質問は仕様違反として扱う。

### 4.6 「わからない」「修正」「引き継ぎ」の共通操作方針

3 つとも「主フローの終端」ではなく「主フローに戻るための分岐」である。
いずれも `W3`（および該当する場合 `W4`）に留まり、状態を後退させない。

#### 「わからない」（`OP-D5`）

3 段の入口として扱う。上から順に試み、解決した時点で `W3` の主作業へ戻る。

1. **AI 調査**: その質問だけを対象に調査する（`#286` / `#295 §4.8`）。結論が
   出れば根拠付きで提示し、開発者は確認するだけでよい。
2. **共同理解**: 調査で確定できない場合、事実 / 翻訳 / 開発者判断の 3 提供元を
   分けたまま対話を続ける（`#328` 系）。「仮説採用」は暫定であり事実にしない。
3. **引き継ぎ**: どちらでも解決しない、または担当外の場合。

「わからない」自体は回答として記録されるが（確定回答なしとして）、質問は
未解決のまま残り、上記 3 段のどこかで解決するまで `W3` の完了条件を満たさない。

#### 「修正」（`OP-D12` / 回答の修正）

- 修正は常に **新しいリビジョン** として記録し、過去の回答を上書きしない
  （現行方針を維持）。
- 修正の影響で再評価が必要になった場合、再評価は自動（`OP-S9`/`OP-S10`）だが、
  **状態の後退は明示確認**（§2.5 基準 C）。
- 自由文のまとめて修正は、常に「変更案のプレビュー → 選択して適用」であり、
  一括自動適用はしない（`#289` の方針を維持）。

#### 「引き継ぎ」（`OP-D6`）

- 引き継ぎ操作は対象項目のカード内に置く（一覧側には置かない、§3.5）。
- 引き継いだ項目は開発者の必須作業から外れるが、**消さない**。`W3`/`W7` に
  「引き継ぎ待ち」として残す。
- 引き継ぎ先の回答は、引き継ぎ元の開発者の回答としては記録しない（`#291`）。
  確定は明示操作で行う。
- 引き継ぎ待ちだけが残った状態は `W7` の終端「引き継ぎ」（§5.4）として表示する。

## 5. 例外・復旧フロー（Issue #346）

### 5.1 例外の分類

| 区分 | 定義 | 主作業への影響 | 表示 |
| --- | --- | --- | --- |
| ブロッキング | 現在の主作業を進められない | 止まる | 現在地の直下に 4 点セット（§4.4）|
| 劣化 | 補助情報・付随機能だけが失われる | 継続 | 該当情報の位置に 1 行 |
| 情報 | 例外ではなく通常フローの分岐 | 継続 | 主作業の中で扱う |

「主作業を継続できる部分障害」= 劣化 + 情報。`R3`/`R4`/`R6` の要素の取得失敗も、
その状態の判断を進められる材料が別に残る場合だけ劣化として扱い、主作業を止めない。
とくに `R3` は判断に必要な根拠なので、代替材料がなければブロッキングになりうる。

ただし「劣化」を名乗れるのは、**その失敗によって欠ける情報が、現在の主作業の
判断に必要でない場合に限る**。同じ処理の失敗でも、既存の有効な結果が残って
いる、または質問などの代替材料が残っていれば劣化、判断材料が何も残らなければ
ブロッキングになる（`E3-a` / `E3-b` と `E4-a` / `E4-b` の分離がその例）。
区分は処理の種類ではなく、**失敗時点で、その状態の判断を進められる材料が
残っているか** で決まる。理解の構築に失敗しても質問で理解を組み立てられる
なら劣化（`E3-b`）、質問すら提示できないならブロッキング（`E3-a`）である。

### 5.3 表示規則

1. **発生するまで出さない**: 復旧操作（`OP-S1`〜`OP-S8` の手動起動）は、対応する
   例外が現在発生している場合にのみ表示する。
2. **同じ場所にまとめる**: 説明・現在地・影響・次の操作を 1 つの枠に置く。
   説明が上部、操作が別パネル、という分離をしない。
3. **戻る条件を書く**: 「何が起きれば通常フローに戻れるか」を必ず 1 行で書く。
4. **過去のエラーを残さない**: エラーは「現在も主作業をブロックしている / 劣化
   させている」場合にのみ表示する。同じ処理がその後成功した場合、および他の
   状態へ遷移した場合は主フローから消し、履歴（`R6`）にのみ残す。
   現行の `last_error` 表示（`interview.tsx:2766-2774`）は成功後も残るため、
   この規則に合わせる必要がある。
5. **劣化で主作業を止めない**: `E3-b`, `E4-b`, `E11`, `E12`（一部スキップ）は、
   いかなる場合も主操作を disabled にしない。逆に `E3-a`, `E4-a`,
   `E12`（生成失敗）は判断材料が存在しないため、劣化として扱ってはならない。
6. **復旧不能なら安全に終える**: 再試行しても解消しない場合、`W7` の「中断」
   または「引き継ぎ」終端（§5.4）へ進める導線を出す。回答・確定・承認は保持
   されたまま残る。この操作は `OP-D14` であり、既存のセッション `status` を
   `closed` にして manual の監査記録を残す。失敗レコード自体は解消せず、再開時に
   `status` を `open` に戻すと再び該当する失敗状態が表示される。
7. **迂回路を作らない**: ブロッキング例外の復旧操作は「同じ処理の再試行」と
   「§5.4 の終端へ安全に抜ける」の 2 つに限る。人間のゲートを飛ばして次状態へ
   進む操作を復旧の名目で追加しない（§8.2）。

### 5.4 終端の定義

`W7` は 3 つの終端のいずれかとして表示される。終端の条件は同時に成立しうる
ため（差分は出たが一部の質問が引き継ぎ待ち、など）、排他性は **first-match の
優先順位** で担保する。`W7` の主操作は状態共通ではなく、**終端ごとに 1 つ**
定める（`W7` 全体に「接続セットアップへ進む」を置くと、中断・引き継ぎ終端で
意味を成さない操作が主操作になってしまう）。

| 順 | 終端 | 条件 | 主操作（1 つ） | 表示 |
| --- | --- | --- | --- | --- |
| 1 | 完了 | 差分レビューが完了している | 接続セットアップへ進む | 何が生成されたか / 未解決事項（あれば）|
| 2 | 引き継ぎ | （完了ではなく）引き継ぎ待ちの項目が 1 件以上ある | 引き継ぎ状況を確認する | 誰に何を渡したか / 戻ってきたときにやること |
| 3 | 中断 | 上記のいずれでもない（承認済み提案 0 件かつ未レビュー提案なし、または `status = closed` で復旧不能時に中断した）| このセッションを再開する | どこまで確定したか / 再開の条件 / 確定内容は保持される旨 |

補足:

- 順 1 が最上位なのは、差分まで到達していれば「次の作業（適用と接続確認）」が
  存在し、それが最も価値の高い次の一歩だからである。この場合に残っている
  引き継ぎ待ちは **終端の区分ではなく未解決事項** として完了表示の中に列挙する。
- 順 2 は「開発者側でできることが無く、他者の回答を待っている」状態。再開の
  引き金は引き継ぎ先の回答であり、その確定は開発者の明示操作（`#291`）。
- 順 3 の「再開する」は、`W2`〜`W5` のうち再開可能な最も手前の状態へ戻る
  操作であり、`status` を `open` に戻した上で §2.2 を再評価する `OP-D14` である。
  戻り要求がある場合は、同じ操作でその要求への承諾（実装前提 D）も manual として
  記録する。未解消のブロッキング失敗は再開後に再び表示される。

## 8. 実装 Issue 化の前提（分割そのものは本 Issue の対象外）

後続の実装 Issue を起票する際、本仕様のどの部分を実装しても **必ず守られる
前提** を明示しておく。分割の単位・順序・粒度は本 Issue では決めない。

### 8.1 実装前提として新たに必要になる永続化された事実

本仕様が要求し、現行に存在しない永続事実は次の 4 点である。いずれも
「表示状態は永続事実だけから一意に決まる」（原則 P9）を満たすために必要で、
1 つでも欠けると再読込前後で表示状態が変わる。具体的な設計（テーブル / API
フィールド / ジョブ表現）は実装 Issue 側で行う（本 Issue の対象外）。

- **A: 差分レビューの完了**（`W6` → `W7` の判定に必要）。現行はクライアント
  限定状態（`lastMaterialization`）でしか表現されておらず、再読込で失われる。
  §2.3 `W6` の完了条件は「開発者が差分を確認したという明示記録」であり、
  ダウンロード等の副作用では代替できないため、専用の記録が要る。
- **B: システム処理の実行中レコード**（`W1` の判定に必要）。`W1` は §2.2 第 1 段
  行 4 で「実行中レコードがある」ことを条件にしているが、現行で永続的な実行
  状態を持つのは `#288` の refresh job だけで、理解の構築・更新、突き合わせ
  build、質問の分類・調査、差分生成はクライアントの `isPending` にしか
  現れない。この範囲のまま実装すると、再読込した瞬間に `W1` が消えて別状態が
  表示される。`W1` を発生させうる処理はすべて、開始・終了・失敗を永続事実
  として持つ必要がある。逆に、実行中レコードを持てない処理は `W1` を発生
  させず、進行中表示を現在地の一時的な補助表示に留める（この選択も実装 Issue
  側で明示すること）。
- **C: `reached_state` と戻り要求**（システムが記録する進行の事実）。
  進捗順序上で現在到達している判断状態（通常は前進し、D の承諾時だけ後退する
  ワークフローチェックポイント）と、後退を引き起こした事実（回答の修正、
  Intent の変更、Capability 構成の変更、snapshot 更新による再レビュー、
  ブロッキング失敗の発生）の識別。どちらもシステムが機械的に導出・記録する。
- **D: 戻り要求への承諾**（開発者の明示判断）。`decision_method: manual` として
  記録する。C とは別の事実として扱うこと — 「今の作業を中断して手前の状態へ
  戻る」は開発者が下す判断であり、システムが観測する進行の事実ではない。
  C と D が揃って初めて、ルール表だけでは実現できない「完了済み状態への後退は
  明示確認」（§2.5 基準 C）が再読込を越えて成立する。

`W1` を発生させうる処理の実行中レコード（B）と、ブロッキング失敗レコードの
**対象状態**（§2.2 第 1 段 行 5 / 8 / 10）は同じ 1 つの実行記録から導出できる
（開始 → 実行中、失敗終了 → 未解消のブロッキング失敗、成功終了 → 解消）ため、
別々の永続事実にはしない。

これ以外の状態判定（`W0-A`, `W0-B`, `W2`〜`W5`, `W7`）は、既存の永続事実（snapshot、
セッション `status`、
`understanding_confirmed_at`、`open_questions`、Q&A の open 件数、
Alignment の `outstanding_counts`、提案の `approval_state`、
`materialization_diff` の有無）から決定的に導出できる。

A〜D はいずれも「表示状態の決定」にのみ用いる事実であり、人間のゲート
（§8.2）を増やしも減らしもしない。内訳は次のとおり。

| 事実 | 種別 |
| --- | --- |
| A 差分レビューの完了 | 開発者の明示判断（`decision_method: manual`）|
| B システム処理の実行中 / 失敗レコード | システムが記録する進行の事実 |
| C `reached_state` と戻り要求 | システムが記録する進行の事実 |
| D 戻り要求への承諾 | 開発者の明示判断（`decision_method: manual`）|

復旧不能時の中断・引き継ぎ終端と再開（`OP-D14`）は新しい状態判定事実を追加せず、
既存のセッション `status`（`closed` / `open`）を使う。ただし操作自体は開発者の
明示判断なので、状態変更には `decision_method: manual` の監査記録を伴わせる。

  差分の適用、観測の開始。いずれも `decision_method: manual` の記録を伴う。
- 対象リポジトリへの書き込み禁止（Principle 5）と、隔離 worktree での実行
  （Principle 8）。
- 推論失敗時のヒューリスティック・フォールバック禁止（Principle 6）。
- `#284`（AI 提案は自動確定しない）、`#285`（疑問の解消は回答の確定と別）、
  `#288`（回答は refresh 失敗を越えて残る）、`#291`（引き継ぎ先の回答を本人の
  回答として記録しない）、`#295`（`accept_current` のみ carry-over）、

### 8.3 実装時に必ず追加すべき検証

- 状態決定: §2.2 の 2 段階評価が、同一のセッション事実に対して常に同じ状態を
  返すこと（順序依存・クライアント状態非依存）。
- 戻り抑止: 未承諾の戻り要求がある間は `reached_state` が表示され、承諾後に
  初めて候補状態へ移ること。承諾は戻り要求ごとに独立であること
  （過去の承諾が新しい戻り要求に流用されない）。
- 未到達操作: §3.2 で「廃止」とした常設要素が、対応する例外が発生していない
  状態で描画されないこと。特に `W6` が差分の存在なしに成立しないこと。
- 主操作と完了条件の一致: 各状態の主操作を実行すると、その状態の完了条件が
  満たされること。`W6` はダウンロードでは完了しないこと。
- 進捗順序: `W0-A` / `W0-B` / `W1` が第 2 段の抑止対象にならず、`reached_state`
  も更新しないこと。特に正常系の `W3`→`W1`→`W4` と `W5`→`W1`→`W6` が抑止に
  捕まらないこと。
- ブロッキング失敗の表示先: 実行中レコードが失敗で終了したあと、対象状態
  （`W2` / `W4` / `W5`）が §2.2 第 1 段の失敗行で選ばれること。失敗より手前で
  できる作業が残っている場合はそちらが優先されること。
- 安全な終端: 未解消のブロッキング失敗があっても、`OP-D14` でセッションを
  `closed` にすると失敗行より先に `W7` が選ばれること。再開で `open` に戻すと
  失敗レコードが再び表示され、中断が失敗の解消やゲート通過として扱われないこと。
  中断による `W7` 表示では `reached_state` が更新されないこと。
- 承認セットと差分の対応: 全提案を承認し終えた直後、差分生成に失敗した直後、
  既存差分より後に承認・編集・却下を行った直後のいずれでも `W5` に留まり、
  `W7` に落ちないこと。
- 劣化の非ブロッキング性: `E3-b`, `E4-b`, `E11`, `E12`（一部スキップ）の発生時に
  主操作が操作可能なままであること。逆に `E3-a`, `E4-a`, `E12`（生成失敗）が
  劣化として扱われず、`W2` / `W4` / `W5` に留まること。
- 迂回路がないこと: ブロッキング例外の復旧操作に、人間のゲートを飛ばして次
  状態へ進む操作（`E4-a` の「突き合わせを行わずに進む」等）が無いこと。
- 終端の排他性: §5.4 の 3 終端が first-match で 1 つに決まり、終端ごとに
  異なる主操作が提示されること。
- 再開: §6.7 の 5 ケースで、再読込前後の表示状態が一致すること。

# 知識・観点・改善手順の効果を検証する仕組みの提案

**日付:** 2026-10-04。**役割:** decision-or-gap-record。**状態:** proposal（未実装・未実験）。
**対象:** `48c52540f6220c57606a986b84e50b8236f725b0` と現在のローカル文書。
ユーザーの依頼は仕組みの提案。現行の運用契約、製品、vendorは本提案では変更しない。

結論は、ユーザー介入直前の状態を保存し、目的・事実・予算を揃えた上で観点の有無だけを変える
反復実験を行うこと。再現の妥当性、観点そのものの効果、必要時に知識を選ぶ手順の効果を別々に評価する。
観点なしの成功は正当な実験結果であり、失敗するまで再現条件を調整してはならない。

## 1. 既存の仕組みから利用する部分

[自己改善手順](../../vendor/evolution-controller-0.1.0-preview.1/self-improvement.md)には旧版との固定課題比較、
後知恵の混入防止、調整外の例、負担・停止の規則がある。
[既存の評価基盤](../03-validation/assistant-answer-quality.md)には、繰り返し・環境・固定課題・未測定の明示がある。
ただし実装は[製品内アシスタントの評価スクリプト](../../apps/control-server/scripts/assistant_eval.py)であり、
開発Agentの会話・作業ツリー・知識検索・試行履歴を介入前へ戻す仕組みではない。
本提案では実行部分を別のローカル評価器として追加し、結果の正本は既存のIP/IRへ接続する。

参照した知識と適合理由:

- [IK-0004](issue-knowledge/entries/IK-0004-unobserved-user-outcomes.md) / EC-P06:
  検査器の成功をAgentの改善効果と混同しない。Agentが実際に残した成果を測る。
- [IK-0017](issue-knowledge/entries/IK-0017-incomparable-metrics-ranked.md):
  要件・条件・測定範囲が違う結果を同じ優劣へ畳まない。
- [EC-LP-0001](../../improvement/local/patterns/EC-LP-0001-premise-validity-v1.md):
  比較時の依存資料・知識・評価器の版固定にC1を参照する。DB競合対策を実験へ機械的に追加しない。
- [EC-LP-0002](../../improvement/local/patterns/EC-LP-0002-fixed-information-v1.md):
  介入前の入力と結果を分離し、観点改訂で過去の実験条件を書き換えない。

いずれも設計上の参照であり、今回の提案を適用成功には数えない。

## 2. ユーザーの指示を、変わったものごとに分解する

メッセージ全体に単一のラベルを付けず、主張・指示の単位で分解する。同じ一文が複数の種類を含む場合もある。

| 種類 | 判断の問い | 扱い |
| --- | --- | --- |
| Vision・UX・運用要件の変更 | 成功とみなす目的・利用者・挙動・制約が変わったか | 新しい要件版を作る。旧要件で妥当だった出力を、後からAgentの失敗へ変更しない |
| 既存要件の明確化 | 以前の文面から合理的に同じ条件を要求できたか | 根拠箇所と当時の曖昧さを記録。解釈が分かれるなら別の評価契約として保持 |
| 新しい事実・観測 | エラー、再現操作、利用環境など、以前は得られなかった情報か | 観点比較の両条件に同じ情報を渡す。事実追加の効果とは別に比較 |
| 調査・設計・検証の観点 | 成功条件は同じで、何を疑い、何を比べ、どこを検証するかが増えたか | 独立した候補観点として版を付け、比較対象にする |
| 具体的な解法の指示 | 修正箇所・コード・アルゴリズムそのものを指定しているか | 解法支援として別に扱う。一般的な観点の効果に混ぜない |
| 権限・資源・再試行 | 使える道具、予算、追加の試行機会が変わったか | 両条件を揃えるか、独立した実験要因にする |

「UX」という語の有無では判定しない。既存の入力保全要件に対して「保存応答の待機中も編集される」と
指摘するのは、要件変更ではなく観測・観点の追加である可能性がある。
直前の本会話の「人の分類確認を待たない」「通常作業では一律参照しない」は、まず運用要件の変更として扱う。
変更後の要件を渡さない群との比較だけでは、観点の効果を示せない。

分解結果には原文の参照、旧契約と新契約の差分、判断根拠、確信度、別解釈を残す。
原文の内容を失わずに分解できたかを確認する。担当Agentが実施し、人の事前確認を待たない。
区別できない場合は「混在・識別不能」として両解釈を保持し、純粋な観点効果を主張しない。
候補観点には「抽象化した文面」「適用条件」「予想される行動変化」を書き、正解パッチの固有名を除く。

## 3. 再現単位は、問題文だけでなく介入直前の状態

ケースを `episode`、実験条件を `arm`、一回の実行を `trial` とする。
介入直前の同一状態から新しい実行を分ける。現在の会話は解決策を既に含むため、そのまま評価Agentへ渡さない。

| 固定・記録するもの | 再現上の意味 |
| --- | --- |
| 要件と受入条件の版、介入前メッセージ | 当時何を解くべきだったか |
| 会話、可視のツール結果、失敗した試行、圧縮・要約状態 | 誤った仮説への固執、文脈量、消費済み予算も状況の一部 |
| commit、未コミットpatch、必要な未追跡ファイル、依存lock、設定 | 同じソースで始める。commitだけで作業状態を表したことにしない |
| DB・画面・未保存draft・非同期イベントの順序 | 画面幅、別パネル、通信待機中の追記などを省略しない |
| Agent実行器、モデル版、推論設定、利用可能な道具・権限、残予算 | モデル更新や追加資源による改善を観点の効果と混同しない |
| 当時のAGENTS/知識/検索索引/メモリのsnapshot | 後から登録したIK・修正記録・解答へのリンクが対照群へ漏れるのを防ぐ |
| 評価器版と評価用入力 | 実験結果を見てから合格基準を動かさない |

隠れた推論状態や取得できない内部状態を保存したとは扱わない。モデル版・seed等も取得できる項目だけを記録し、
不明は不明とする。seedは利用可能なら記録するが、同じseedを完全な同一実行の保証とはしない。
外部サービスは必要な状態をfixture化し、Agentの新しい操作に応じて応答する。
過去のツール出力を呼び出し内容によらず順番に返す方式では、異なる解法を正しく比較できない。

再現には2種類を分ける:

- **介入直前からの続行:** 行き詰まった状態への救済効果を測る。直前の履歴と残予算を保持する。
- **課題の初期状態からの実行:** 通常の改善過程で、知識をいつ参照すると役立つかを測る。

履歴を消した新規実行の成功を、介入直前の状況が再現できた証拠にしない。
権限内で必要な情報だけローカル保存する。秘密値は含めず、除去で失われる再現条件を明記する。
過去ケースで情報が欠ける場合は後知恵で補完せず、「復元不完全」として扱う。

## 4. 最初に行う比較

新要件・追加事実・権限の変更があれば、まずそれらを共通入力Xへ入れる。
純粋な観点追加ならXは介入前の入力のまま。全群で同じ作業状態、Agent、環境、追加作業予算を使う。

| 条件 | Agentへ与えるもの | 比較で分かること |
| --- | --- | --- |
| A 続行 | Xのみで同じ追加作業機会を与える | そのまま続けても解ける頻度 |
| B 一般的な再検討 | X + 対象観点を含まない一般的な再検討の指示 | 単にもう一度考えることの効果（B−A） |
| C 観点追加 | X + 候補観点 | 再検討に加えた具体的な観点の効果（C−B）、総支援効果（C−A） |

Bは無作用の「偽薬」ではなく、それ自体が有効かもしれない比較対象。
メッセージの役割・投入時点・長さ・口調を可能な範囲で揃え、予算は入力の観点分も含めて記録する。
観点群だけに追加時間、正解を含む出典、強いモデル、便利な道具を与えない。
指示中の具体的解法を除けない場合は、原文支援と抽象観点を別群にし、原文支援の成績を観点へ転記しない。

各trialは独立したsandbox・会話・書込み先・キャッシュで実行する。
実験中は他trialの結果や更新済み知識を見せず、評価用テストと正解例もAgentの読める領域から分離する。
候補知識や手順の更新は一つの比較batchが終わってから行う。

同じ課題・環境条件を組にして実行順をランダム化し、複数回繰り返す。
反復とブロック化を用いるのは、課題や実行時期の差を観点の効果に混ぜないため。
[NISTの実験設計](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)を参照。

## 5. 観点なしでも解けた場合の切り分け

まず「修正前の成果が評価器で失敗し、修正済み成果は成功する」ことを確認する。
修正前でも合格するなら評価器が弱いか、問題の条件が消えている。
これはAgentを再び失敗させることとは別の確認であり、Agentが修正できる能力を否定しない。

その上で、当時の課題を残した再現と、ある要素だけを除いた再現を比較する。

| 再現条件 | 観点なし | 観点あり |
| --- | --- | --- |
| 当時の要素を保持 | 成功率・失敗の型・費用 | 同じ指標 |
| 疑わしい要素を1つだけ除去 | 同じ指標 | 同じ指標 |

除去候補は元の記録に存在するものから選ぶ。例えば会話の失敗履歴、隣接パネル、通信遅延、
保存中の編集、残予算、依存資料の古さ。全てをまとめて削ると、どれが効いたか分からない。
要素の欠落で課題が不可能になる場合もあるため、「省略すると必ず簡単になる」とは仮定しない。
外した要素・仮説・比較順を結果を見る前に決め、版を残す。最初の無観点成功も記録から除外しない。

| 観測結果 | 支持される解釈 | 次の処理 |
| --- | --- | --- |
| 修正前成果が再現環境でも合格してしまう | 課題または評価器の再現不足 | 実験を無効扱いにしてfixture/評価器を直す |
| 当時の要素を戻すと無観点の成功率が下がり、対応する失敗が増える | 省略で課題が変わっていた可能性 | 要素を再現契約へ追加。観点との相互作用も報告 |
| 要素を保持しても成功・失敗が混在し、観点で成功率や費用が改善する | 観点が解決の安定性・効率に寄与 | 能力の新設ではなく失敗確率低減として評価 |
| 要素を保持し、同じ環境で無観点が安定して成功する | 現在の条件では観点の上乗せが小さい可能性 | 失敗を作るために難化しない。通常参照を減らす候補 |
| モデル・道具・予算・記憶が当時と違う | 環境変更・情報漏れとの交絡 | 当時の因果判定は保留し、現在環境の効果として別集計 |
| trialが少なく差の推定幅が大きい | 判定不能 | 事前に決めた追加batchか保留。効果なしと同一視しない |

欠落要素と実行ばらつきは同時に存在し得る。二者択一に固定しない。
繰り返しだけで「過去の1回は乱数が原因だった」と証明することはできない。
保存できなかった状態があれば、判定は「観測した条件下でばらつきと整合」「履歴の原因は未識別」までとする。
基盤資源もAgentの成績を変え得るため、モデルの乱数性と環境揺れを別に記録する。
[基盤条件によるAgent評価の変動](https://www.anthropic.com/engineering/infrastructure-noise)が参考になる。

## 6. アウトプットの比較と採点

比較画面・レポートは、出力の文章diffに加えて次の情報を同じ行に並べる。

| 比較対象 | 指標・証拠 |
| --- | --- |
| 最終成果 | 固定した受入テスト、残った不具合、誤変更、必要条件への違反 |
| 調査・検証の行動 | 注目した条件、実行した再現操作、調べた対象、追加したテスト |
| 費用 | 成功率とあわせた時間・token・tool呼出し・追加試行・変更量・記録費用 |
| 知識利用 | 提示されたか、参照したか、実際の操作に反映されたか。自己申告だけで判定しない |
| 不適合への影響 | 問題のないケースで無用の調査・誤修正・予算超過を増やしていないか |

「観点の語を口にした」だけでは利用成功にしない。別の妥当な方法で解けた場合も成功とする。
観点の利用有無は作用を理解する補助指標で、最終成果の成績を観点の採用へ条件付けない。
成果と環境状態を採点し、trialを複数回評価する構成は
[Agent評価の実務整理](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)とも整合する。

評価器は候補を作る実行から分離し、条件名を伏せ、提示順を入れ替えて採点する。
自動テストを優先し、意味評価は固定rubricと根拠箇所を返す評価Agentで補う。
判定不一致・自動評価不能は保留または評価器の調査へ戻し、人の分類確認を定常ゲートにしない。
主観的な実利用者価値をモデル採点だけで実測したとは扱わない。
評価器が想定解以外を不当に落としていないか、既知の正解・不正解・別解で先に検査する。

試行の有効性エラー（fixture破損など）と、Agentが予算内に解けなかった失敗を区別する。
失敗・timeoutを都合よく除いて成功trialだけの時間を比べない。成功率と全trialの消費を併記する。

## 7. 反復回数と結論の強さ

最初の各条件5回は、実行器・漏えい・評価器を点検するpilotとし、効果認定には使わない。
pilot後に主要指標、意味のある最小差、許容費用増、必要標本数、最大予算、終了条件を固定する。
必要標本数は成功率と検出したい差に依存する。例えば各条件30回を上限にしても、その回数で
十分な検出力があるとは限らず、予算内で区別できなければ「未確定」を返す。
これは初期案であり、有料実験の実行許可・予算設定を意味しない。

成功率の差と不確かさの区間を報告し、単発の勝敗や「有意差なし」だけで採否を決めない。
同一ケースの反復は当該ケースの確率推定であり、異なるケースの独立適用件数ではない。
複数課題への一般化は課題単位で評価し、同系譜・派生ケースをまとめて集計する。
実行器・モデル版・投入時期を揃えた比較内で推定し、別モデルへ結果をそのまま持ち越さない。
都合のよい差が出るまで反復することを避け、固定標本か、事前に選んだ逐次評価方式で終了する。

採否は「有効」「安定性に寄与」「条件限定」「無効の証拠あり」「逆効果」「未確定」「実験無効」を区別する。
差が小さいことを十分な精度で確認した場合は参照不要の条件を追加する。

## 8. 観点の効果から、改善ループの自己改善へ

観点を強制的に渡して有効だったことと、必要時に検索・選択できたことは別である。
次に、同じ知識snapshotを使って次の運用を初期状態から比較する。

| 運用条件 | 調べること |
| --- | --- |
| 追加知識なし | 通常の自律改善の基準 |
| 困難・行き詰まりを判断したときだけ検索 | 現行方針の総効果。検知・検索・適合判断・投入時機・記録の費用を含む |
| 実験側が適合観点を指定時点で供給 | 観点を届けた場合の参照比較。万能な上限とは呼ばない |

必要なら常時参照も比較へ追加し、選択的参照による節約を測る。
各運用の成功率・費用・不要な参照・見逃しを、条件へ割り当てた全ケースで比較する。
自分で行き詰まりを検知できたケースだけを分母にすると、見逃しが消えるため避ける。
人が介入した失敗ケースだけの成績は「救済効果」であり、通常運用全体の効果へ一般化しない。
通常案件や、知識不要・観点非適合の案件も少数の評価用ケースとして含める。

結果に応じた更新先:

- 観点を渡せば有効だが通常は出てこない → 検知・検索語・索引・推薦時機を修正する。
- 検索はできるが誤適合する → 適用・非適用条件を修正する。
- 観点を渡しても変わらない/悪化する → 観点・原因仮説を修正し、不要な利用を止める。
- 成果は良いが費用が過大 → 参照条件・知識の長さ・記録量を縮める。
- 再現が弱い → 製品知識の効果判定を保留し、capture/fixtureを改善する。

手順v0→v1の改訂時は、知識集合・モデル・課題を固定して運用だけを比較する。
知識追加と検索手順変更を同時に評価したい場合は、旧/新知識 × 旧/新手順の4条件を使うか、
同時変更の総効果とだけ報告して個別の寄与を断定しない。
調整に使ったケースと、候補作者に見せない評価ケースを分離する。
同じ失敗を見て何度も手順を直した後、その同じ失敗の成功だけで一般化しない。
評価用ケースを調整へ使った時点で開発用へ移し、別の評価ケースを用意する。

登録はcandidateとして即時に行い、実験結果は採用・修正・保留・撤回の根拠としてIRへ記録する。
知識や手順の使用版から結果へ逆リンクし、条件と負担を更新する。人の事前確認は不要。
人の介入は、顕在化した問題を自律改善できていないと人が発見した場合という現行方針を維持する。

## 9. 保存構成と小さく始める手順

提案する配置（以下はまだ存在しない。通常作業の必須ファイルではない）:

```text
improvement/evaluation/
  episodes/<id>/manifest.json       対象版・入力・再現要素・欠落・ハッシュ
  episodes/<id>/intervention.json   要件/事実/観点/解法/資源の分解と根拠
  experiments/<id>/design.json      各群の差分、割付、評価器、予算、終了条件
  runs/<id>/trial.json              実行条件、成果参照、採点、費用、失敗理由
  reports/<id>.md                   全trialの比較と次の判断
```

機密を含み得る入力・snapshot・実行ログはローカル専用の保管先へ置き、Gitには非機密のmanifestと
参照・合成fixture・集計だけを置く。snapshotの実体を消した場合は再現不能を明示する。
manifestのID・hashだけで完全再現できるとは扱わない。

構成要素は取得、介入分解、再現検査、条件別実行、採点・集計、既存知識への還流。
常駐の全会話解析は初期段階では作らない。ユーザー訂正・行き詰まり・新観点の発見をトリガーに、
その時点で利用可能な介入前の記録と成果を保存する。将来の実行器は直前の小さなcheckpointを保持し、
トリガーが発生したときだけ評価ケースへ昇格させる。既に失われた状態を推測で再現済みにしない。

1・2で元の会話状態が取得できなければ「コード上の条件を復元した合成ケース」として始める。
それで当時のAgent失敗の原因まで説明できたとは報告しない。
最初は1ケースのfixture・比較レポートを作り、次に反復、最後に手順選択の比較へ広げる。
通常の開発を実験準備待ちにせず、候補の利用と効果の未確認表示を両立させる。

## 10. この仕組みの受入条件

- 要件変更だけの介入を観点効果と誤計上しない。混在時は分解できない部分を示す。
- 介入前の入力と新しい知識・解答の隔離が検査できる。
- 修正前の既知不具合を評価器が検出し、妥当な別解を受け入れる。
- 観点なしで成功したtrialも含め、全trialの成果・費用・無効理由を比較できる。
- 再現要素の違い、実行ばらつき、環境変更を別に示し、不明を不明と結論できる。
- 強制的な観点供給の効果と、必要時の知識利用・手順改訂の効果を分離できる。
- 結果から知識・手順の条件を更新でき、人の分類確認待ちを作らない。

実装時に確認が必要な点は、開発Agent実行器から取得・復元できるcheckpointの範囲、
使用モデル版の固定可否、実験用の隔離環境、試行予算。今回これらの実行可否や実効果は未検証。

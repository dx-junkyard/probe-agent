## R1 / P1 — 再認証直後のユーザー情報取得失敗で下書きが消える

**関連: UX-06（再認証時の入力保全）。**

### 再現手順

1. ログイン済み画面で未保存の入力を作る。
2. APIが401を返し、再認証ダイアログを表示させる。
3. 再ログインのPOSTは成功させ、その直後の`GET /auth/me`を500または通信失敗にする。
4. 接続エラー画面から再試行し、同じ利用者で復帰する。

**実際:** 元の入力欄は空になる。今回の追加テストでも、期待値`unsaved work`に対して空文字になった。

**原因:** `fetchMe()`が取得失敗を捕捉した際に`setUser(null)`を実行する。AppLayoutはユーザーがない場合にエラー画面へ置き換わるため、フォームがアンマウントされる。さらに`login()`は`fetchMe()`が失敗しても成功扱いで続行し、`sessionExpired`解除とキャッシュ消去まで行う。

**修正案:** 起動時の認証確認と、既存画面を維持した再認証確認を分ける。確認不能の間は業務操作を遮断しつつフォームを保持し、再認証ダイアログ内で再試行できるようにする。同じ利用者か確認できた後にのみ再開する。異なる利用者が確定した場合の入力破棄・隔離も維持する。

**追加テスト:** POST成功→`/auth/me`の500・ネットワーク失敗・タイムアウト→同一利用者で復旧、の全経路で入力を保持すること。

根拠: `apps/dashboard/src/api/auth.tsx:77-88,140-150`、`apps/dashboard/src/components/layout/app-layout.tsx:41-53`。

## R2 / P2 — 履歴の「戻る」やプログラムによる遷移が未保存ガードを通らない

**関連: UX-03（画面離脱時の入力保護）。新しい登録hookだけでは既存ガードの対象外経路を保護できていない。**

### 再現手順

1. OverviewなどからRepositoryまたはExperimentsへ移動する。
2. 未保存の設定・下書きを入力する。
3. SPA内のブラウザー履歴を戻る。または`navigate(...)`で別ページへ移動する操作を行う。
4. 再び編集画面を開く。

**実際:** 破棄確認なしで画面を離れ、ページのローカルstateを失う。追加テストでは、本物の`UiDraftProvider`と`useUnsavedChangesGuard`にdirtyフォームを登録して`navigate(-1)`を実行し、確認関数が一度も呼ばれないことを再現した。

**原因:** 共通ガードが監視するのは`a[href]`のクリックと`beforeunload`だけ。SPA内の履歴移動は通常`beforeunload`を発生させず、`navigate(...)`もアンカークリックではない。AppLayoutのsnapshot通知などにもプログラムによる遷移がある。

**修正案:** ルーターの遷移を一貫して保護できる仕組みに統合する。アンカークリックだけの対策にしない。キャンセル時は現在のURLと入力を保持し、破棄を選んだときだけ遷移する。既存の確認との二重表示を避ける。

**追加テスト:** dirty状態でPOP（戻る／進む）・PUSH・REPLACEを実行し、キャンセルでは入力を保持、了承では遷移する。実ブラウザーの履歴操作でも確認する。

根拠: `apps/dashboard/src/lib/ui-draft.tsx:190-203,256-268`、`apps/dashboard/src/pages/experiments.tsx:217`、`apps/dashboard/src/pages/repository.tsx:760`、`apps/dashboard/src/components/layout/app-layout.tsx:94-97`。

## R3 / P2 — Experimentの作成応答待ち中に追記した内容が成功時に消える

**関連: UX-03（保存中の入力保護）。変更前にもあり得た挙動だが、本Issueの受入条件に対する残存問題。**

### 再現手順

1. Experimentの評価目的・Snapshot・2候補を入力する。
2. 作成ボタンを押し、POSTの応答を遅延させる。
3. 応答を待っている間に、候補1のpatchを追加編集する。
4. 元のPOSTを成功させる。
5. 作成フォームを再度開く。

**実際:** 送信後に追記した内容も初期化される。追加テストでは、応答待ち中に入力した`diff a plus unsaved update`が空文字になった。追記内容は元のPOSTには含まれておらず、保存もされていない。

**原因:** 送信中でもフォームは編集可能だが、応答成功時に送信時点との差分を確認せず`resetForm()`を呼ぶ。ダイアログを閉じて下書きを再開する経路でも同じ競合が起こり得る。

**修正案:** 送信したdraftのrevisionを保持し、現在のdraftと一致する場合だけ初期化する。不一致なら保存完了した内容と未保存の追記を区別して残す。あるいは送信中の編集を一貫して抑止する。

**追加テスト:** POSTを遅延させた状態で追記してから成功応答を返し、未送信内容が保持されるか、そもそも追記操作ができないことを確認する。

根拠: `apps/dashboard/src/pages/experiments.tsx:240-265,272-273,555-557`。

## R4 / P2 — Repositoryの保存成功後も「未保存」が残る

**関連: UX-03。追加されたdirty判定と既存の保存時正規化が一致していない。**

### 再現手順

1. Include Patternsに末尾改行を含む`*.py\n*.ts\n`を入力する。
2. Save Configurationを押す。
3. 保存済み設定の再取得を完了させる。

**実際:** 保存に成功しても「未保存の変更があります」が残る。画面離脱時の破棄確認も残り、同じ内容を再保存しても解消しない。追加テストで再現した。

**原因:** 送信時の`textToPatterns()`は空白・空行を除去する一方、dirty判定は入力の生文字列と保存済み配列をjoinした文字列を比較する。入力stateは正規化後の保存値へ同期されない。

**修正案:** dirtyも保存時と同じ正規化を適用した値同士で比較する。保存成功時に同期する方法を選ぶなら、R3同様、送信後の追加編集を上書きしないようにする。

**追加テスト:** 末尾改行・空行・前後空白のあるInclude/Exclude Patternsについて、保存と再取得後にdirtyが解除され、意味のある追加編集では再びdirtyになること。

根拠: `apps/dashboard/src/pages/repository.tsx:750-771`。

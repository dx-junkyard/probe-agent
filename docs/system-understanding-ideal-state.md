# System Understanding の理想状態と現在の構造的課題

## 1. この文書の目的

この文書は、`probe-agent` が長期的に目指す System Understanding の全体像と、
現時点で不足している要素・枠組みを定義する。

個別機能の詳細仕様や実装順序を決める文書ではない。今後の Issue や設計が局所的な
改善に偏り、System Understanding の本来の目的から外れることを防ぐための上位方針で
ある。既存の安全境界、承認ゲート、各機能の詳細仕様は引き続き
`docs/project-intelligence.md` などを正とする。

追跡 Issue: [#327](https://github.com/dx-junkyard/probe-agent/issues/327)

## 2. 目指す状態

`probe-agent` の System Understanding は、リポジトリ内の文書を要約する機能でも、
コード構造を一覧化する機能でもない。

目指すのは、次の能力を持つ、証拠駆動かつ目的指向の継続的な調査システムである。

> 人間が何を判断しようとしているかを起点に、コード、文書、設定、契約、データ構造、
> 実行経路、運用情報、実行時観測を横断して証拠を集め、事実・推論・仮説・不明点・
> 矛盾を区別したシステム像を構築する。残った不確実性に対して追加調査を行い、
> 最後に、人間にしか答えられず、かつ答えによって重要な判断が変わる質問だけを提示する。

この状態では、System Understanding は一回の生成処理ではなく、以下の閉じたループに
なる。

```text
調査目的を定める
  → 証拠の所在と欠落を把握する
  → 複数のシステムビューを構築する
  → claim と競合仮説を作る
  → 仮説を区別できる追加調査を行う
  → 残った不確実性の情報価値を評価する
  → 必要な質問だけを人に聞く
  → 回答・新しい証拠・実行時観測で理解を改訂する
```

## 3. 理想状態を構成する能力

### 3.1 目的指向の調査

調査は、常に「何を理解・判断するためか」を明示して始める。

- システム全体のオンボーディング
- ある Capability の責務と所有境界の確認
- 変更影響範囲の特定
- 障害原因や復旧経路の理解
- Probe Point や改善対象の選定
- セキュリティ、性能、互換性などの制約確認

目的によって必要な証拠、許容する不確実性、深掘りする経路は異なる。既定の全体理解も
提供するが、すべての調査で同じ情報を同じ深さまで読むことを前提にしない。

### 3.2 幅広い証拠の収集と、収集できなかった事実の可視化

証拠源には少なくとも次の層がある。

- リポジトリ構造、依存関係、ビルド・起動定義
- 複数言語のコードシンボル、import、呼び出し関係
- API、メッセージ、ジョブ、CLIなどの入口と外部契約
- DB schema、migration、状態遷移、データ所有境界
- README、設計文書、ADR、運用手順
- CI/CD、コンテナ、インフラ、監視・復旧定義
- テストが表現する契約と代表シナリオ
- Trace、評価結果、エラー率、実行経路などのruntime reality
- 人間が確認・訂正した意図、制約、業務判断

すべてを一つのモデルに推測させるのではなく、構造的に抽出できる事実は決定的処理で
抽出し、自由度のある解釈だけをreasoning modelへ渡す。

対象外、サイズ超過、未対応形式、解析失敗、予算による省略も証拠カバレッジの一部として
記録する。「見つからなかった」と「探していない」を混同しない。

### 3.3 複数ビューからの全体像構築

単一の巨大な要約ではなく、互いに関連付けられた複数ビューを構築する。

- Context: 利用者、目的、外部システム
- Topology: サービス、アプリ、ライブラリ、デプロイ単位
- Capability: ユーザー価値、責務、所有境界
- Behavior: 代表ユースケースの入口から出口までの処理
- Data: 正本、読み書き、状態遷移、整合性境界
- Runtime: 実際に観測された経路、頻度、失敗、性能
- Operations: デプロイ、監視、障害伝播、復旧
- Trust: 認証、認可、秘密情報、ネットワーク・権限境界

各ビューは同じ証拠ID、シンボル、入口、Capability、Componentなどを介して接続する。
異なる機能が独立した「システム像」を持ち、利用者がどれを信頼すべきか判断できない
状態を避ける。

### 3.4 claim と仮説の明確な区別

理解の各項目は少なくとも次を区別する。

- **事実**: 構造解析、実行結果、人間の明示判断などで確認済み
- **推論**: 複数の証拠から導いた説明
- **仮説**: 追加検証が必要な候補説明
- **不明点**: 現在の証拠では判断不能
- **矛盾**: 権威や時点の異なる証拠が両立しない

仮説は単なる低confidence claimではない。良質な仮説は次を持つ。

- 仮説を支持する証拠
- 競合する説明
- 正しければ観察されるはずの結果
- 反証条件
- 競合仮説を区別するための次の調査

Confidenceはモデルの自己申告だけで決めず、証拠の種類、独立性、新鮮さ、権威、
直接性を反映する。文書内の同じ主張が複数回現れることを、独立した裏付けとは扱わない。

### 3.5 反復可能なInvestigation

調査可能な疑問に対しては、一度のキーワード検索と一度のモデル呼び出しで結論を
出すことを前提にしない。

必要に応じて次を反復する。

1. 既存のgraph、symbol、entrypoint、contract、runtime factsから候補を選ぶ
2. 関連箇所を行・シンボル単位で読む
3. 新たに判明した識別子、呼び出し先、データ、設定を追う
4. 証拠が十分か、競合仮説を区別できたかを評価する
5. 予算内で追加探索するか、`unresolved`として終了する

探索予算、読んだ証拠、読まなかった候補、終了理由は監査可能にする。調査は固定された
snapshotに対して再現可能で、対象リポジトリを変更しない。

### 3.6 情報価値に基づく質問選定

人間への質問は、単にconfidenceが低い項目を並べたものではない。質問候補ごとに、
少なくとも以下を考慮する。

- 現在の不確実性
- 答えによって変わる理解・判断・安全性
- 影響するCapability、Flow、データ、変更候補の範囲
- コードやruntime調査だけで解消できる可能性
- 回答を得るコスト
- 他の複数の不明点を同時に解消する効果
- 今の作業をブロックしているか

概念的には、質問の価値を次として扱う。

```text
質問価値
  = 不確実性の大きさ
  × 判断への影響
  × 他の不明点を解消する波及効果
  ÷ 調査・回答コスト
```

厳密な数値スコアを必須とはしないが、質問の優先理由がこの考え方で説明できなければ
ならない。実装事実を調べずに人へ転嫁しない。意味的に同じ質問を言い換えて繰り返さない。

### 3.7 継続的な検証と改訂

生成された全体像は完成品ではなく、検証可能な現在のモデルである。

- 主要claimはsnapshot内の実在する証拠へ戻れる
- 代表フローについて、入口から状態変化と外部境界まで説明できる
- runtime realityとの一致・不一致・未観測・古さが分かる
- 新しいsnapshotで、変わったclaimと無効になった証拠を識別できる
- 人間の訂正は後続の理解へ反映され、拒否した解釈が無断で復活しない
- どのreasoning runがどの理解を生成したか追跡できる

構造やスキーマの正しさだけでなく、現実的なfixtureやdogfooding対象について、
期待するシステム像、代表フロー、重要な矛盾、質問の妥当性も評価する。

## 4. 現在の `probe-agent` がすでに持つ基盤

現在の実装には、理想状態へ進むための重要な基盤がある。

- committed-files-onlyのRepository Snapshotとhash provenance
- Python ASTによるsymbol・entrypoint・限定的なflow解析
- Markdown chunk単位のevidence-bound claim抽出
- Understanding Graphとdocs/code reconciliation
- source-authored metadata、Capability Hierarchy、Feature Map
- revision、drift、gap、human alignmentの永続化
- Question Routerによる`human_only` / `system_researchable` / `hybrid`分類
- read-only Investigation Agentとruntime facts
- evidence範囲検証、reasoning run監査、fail-closed
- 人間の確認・訂正・承認と実行を分離する安全境界

今後の改善はこれらを置き換えるのではなく、共通の証拠・claim・調査モデルの下で
接続し、欠けているループを埋める方向で行う。

## 5. 現時点で不足している要素・枠組み

### 5.1 調査目的と探索計画の接続

System ProfileやIntent Briefは存在するが、標準のUnderstanding buildは固定された
一連の処理を実行する。調査目的に応じて、どのビュー、証拠、フロー、不確実性を
優先するかを決める共通のInvestigation Objective / Planがない。

### 5.2 証拠カバレッジの幅と一貫性

主要な意味解析はPythonとMarkdownに強く依存している。複数言語、API schema、
DB migration、データモデル、インフラ、CI/CD、運用・監視情報は、snapshotに存在しても
System Understandingの第一級の構造化証拠にならないことがある。

また、機能ごとにコンテキスト選択・切り詰め・証拠検証の規則が異なり、何が読まれ、
何が省略されたかの共通ビューがない。

### 5.3 代表Behavior / Data / Operationsビュー

Flow Explorerは存在するが、標準ビルドが主要入口を比較し、代表ユースケースを選び、
入口から出口までの経路を全体理解へ統合するわけではない。データ正本、状態遷移、
トランザクション、障害伝播、復旧経路も共通ビューとして不足している。

### 5.4 runtime realityの全体理解への統合

runtime factsとRuntime Reality Checkは存在するが、通常のUnderstanding reviewの
標準証拠として常に静的理解と照合されるわけではない。静的claimと実観測の関係を、
`match` / `mismatch` / `unobserved` / `stale`として各ビューへ一貫して反映する
枠組みが必要である。

### 5.5 理解モデルの分散

System Profile Draft、Feature Map、Understanding Graph、Capability Hierarchy、
Interview `current_understanding`、Flow Graph、Runtime Realityなどが、それぞれ
有用な情報を持つ一方、共通のclaim identity、evidence identity、authority、
freshness、revision関係で十分に統合されていない。

単一の巨大モデルへ統合する必要はないが、「同じ対象について異なる説明がある」ことを
検出し、利用者がどの説明の根拠・権威・時点を信頼すべきか判断できる必要がある。

### 5.6 仮説・反証・競合説明のモデル

現在はclaim、confidence、gap、open questionを扱えるが、競合仮説、予測、反証条件、
検証計画が第一級の概念ではない。そのため、低confidence項目を人へ確認する方向には
進めても、証拠を追加して自律的に仮説を絞る方向が弱い。

### 5.7 Investigationの探索能力

個別質問の調査は、ファイルパスへのキーワード一致と限定された一回のreasoningに
依存する部分が大きい。symbol、import、call graph、entrypoint、API、data、
Capability、全文検索、runtime factsを横断した反復検索と、追加探索の停止条件が
共通化されていない。

### 5.8 質問のValue of Information

質問にはcategoryやpriorityがあるが、質問がどの判断を変え、何をブロックし、
いくつの不明点を解消するかを明示して優先する枠組みがない。重複判定も意味的な
question identityではなく、文面やモデル判断に依存する。

### 5.9 意味品質の評価

既存テストは状態遷移、schema、System分離、fail-closed、証拠範囲などを強く保証する。
一方、大規模・多言語・文書矛盾・runtime不一致を含む対象で、全体像、代表フロー、
仮説、質問が実際に有用かを継続評価するevaluation corpusと品質指標が不足している。

## 6. 今後の設計が外してはならない原則

1. **証拠を先に、解釈を後にする。**
   構造的事実とreasoningによる解釈を混ぜない。
2. **一回の巨大プロンプトで全体理解を作らない。**
   取得、関連付け、仮説、検証、質問を分離する。
3. **「見つからない」を「存在しない」と解釈しない。**
   未探索、未対応、予算超過、解析失敗を区別する。
4. **人間への質問は調査の代替ではない。**
   システムから調べられることを先に調べる。
5. **仮説を事実へ昇格させる条件を明示する。**
   Confidenceだけで事実化しない。
6. **runtime observationも無条件に正解としない。**
   観測範囲、新鮮さ、sampling、環境、snapshot対応を保持する。
7. **既存の人間承認・安全ゲートを緩和しない。**
   理解が深まることと、自動適用・自動実行の権限は別である。
8. **共通化は単一巨大モデル化を意味しない。**
   各ビューの役割を保ちつつ、identity、evidence、authority、revisionを接続する。
9. **失敗と不確実性を可視化する。**
   heuristicで成功に見せかけず、`unresolved`や部分的coverageを正直に返す。
10. **意味品質を評価可能にする。**
    構造的なcontract testだけで完成としない。

## 7. この理想状態に含めないもの

- 対象リポジトリへの無承認の変更
- 理解結果に基づく自動デプロイ、自動採用、自動policy変更
- すべての証拠を無制限にLLMへ送ること
- 単一のconfidence scoreで安全性や正しさを表すこと
- 人間の業務判断をコードから推測して確定すること
- すべての言語・frameworkを同時に実装すること
- 既存のFeature Intelligence、Interview、Flow、Runtime機能を作り直すこと

## 8. 到達を判断するための大枠

詳細なAcceptance Criteriaは今後の個別設計で定めるが、少なくとも次を説明・検証できる
状態を目標とする。

- ある理解が、どの調査目的、snapshot、証拠、reasoning runから生まれたか
- どの情報源を探索し、どこが未探索・未対応・省略されたか
- 主要なContext、Capability、Behavior、Data、Runtime、Operations、Trustビュー
- 重要claimが事実・推論・仮説・不明・矛盾のどれか
- 仮説を支持・反証し、競合仮説を区別する次の調査
- 人間へ聞く前に実施したsystem-researchableな調査
- 各質問がどの判断を変えるため、なぜ今聞く価値があるか
- 新しいsnapshot、runtime observation、人間の訂正で何が変わったか
- 現実的な評価対象で、全体像と質問の意味品質が維持・改善されたか

この枠組みを満たすことで、`probe-agent` は「証拠付きの部分理解を安全に蓄積する
システム」から、「目的に応じて探索を反復し、検証可能な全体像と高価値な質問を
継続的に作るシステム」へ進化する。

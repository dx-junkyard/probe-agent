# UX評価用ダミーデータの生成指示文

**文書の役割:** guide-or-runbook  
**状態:** draft（生成指示文。データ生成・製品評価は未実施）  
**作成時点:** 2026-10-04  
**対象:** 小規模プロジェクトから成長過程までの、理解・助言・観測・判断のUX評価

## 使い方

次節の指示文をデータ生成担当のAIへ渡す。初回は既定値の `S0 / starter` を使い、
プロジェクト資料、ペルソナ、投入台本、評価基準を小さく作る。実行時観測まで確認する
場合は `artifact_mode=executable` にする。今回は指示文の作成までで、投入や評価は行っていない。

成長には二つの軸がある。対象プロジェクトの成長は同じ架空プロジェクトの段階差分で、
probe-agent自体の成長は固定した同じデータを異なる製品revisionへ投入して評価する。
この二つを同時に変えず、何によって結果が変わったか比較できるようにする。

生成物はprobe-agentへの一括インポート形式ではない。資料、対話で伝える情報、実行入力を
分けた評価素材であり、利用可能な画面・API・SDKへの対応を投入台本で確認する。

### 別フォルダ・別プロジェクトで使う場合

次節のコードブロック全体だけで初回生成を依頼できる。過去の会話やprobe-agentの
リポジトリは必須ではない。`output_dir` は実行先の作業ディレクトリを基準に指定する。
末尾の仕様リンクは本リポジトリ内で確認するための補足であり、生成時の必須入力ではない。
文書ファイルを単独で移動した場合、これらの相対リンクは使えなくなる。

| 用途 | 別環境へ渡すもの | 参照元がない場合 |
| --- | --- | --- |
| 初回の資料・ペルソナ生成 | 次節の指示文全体 | 単独で生成可能 |
| 架空ツールの実装・単体テスト生成 | 指示文全体、`artifact_mode=executable` | SDKに依存しない実装を生成可能 |
| 製品の画面・API・SDKへの具体的な接続 | 指示文、明示した製品コードまたは仕様資料 | 接続部分は未確認として残す |
| 次段階の生成 | 指示文全体、追加指示文、前段階の生成物とmanifest | 不足分を特定し、連続性に依存する生成は保留 |

生成先プロジェクトのコードを、自動的にprobe-agentのコードや架空ツールの既存実装と
解釈しない。生成後の評価には公開用の資料だけを渡し、この指示文や評価者用資料を
評価対象の入力に含めない。

## コピーして使う生成指示文

````text
あなたは、probe-agentのUXを評価・改善するための架空プロジェクトとペルソナを設計する担当です。
以下の条件で評価用データセットを生成してください。製品が優秀に見える物語ではなく、
判断に必要な証拠・制約・不明点を含み、失敗や改善余地を発見できる素材を作ってください。
今回の作業は評価素材の生成までです。probe-agentへの投入、外部通信、本番変更は行いません。

【パラメータ】
- dataset_id: triage-growth-v1
- stage: S0
- size: starter
- artifact_mode: documents（documents / executable）
- scenario_seed: 20261004
- language: ja
- target_domain: 小規模組織の社内問い合わせ受付・担当振り分け
- output_dir: ./triage-growth-v1（実行開始時の作業ディレクトリからの相対パス、または指定した絶対パス）
- reference_mode: standalone（standalone / product-aware）
- probe_agent_source: なし（product-aware時だけ、製品リポジトリのルートを明示）
- reference_materials: なし（任意の添付資料、または明示したファイルパスの一覧）
- existing_dataset: なし（継続時は前段階の生成物とmanifestの添付、または所在パスを明示）
- probe_agent_revision: 未指定
- target_implementation: 未確認（probe-agent側の機能の実装状況。架空ツールの実装状況とは別）

【0. この指示文だけで実行するための前提】
probe-agentは、ソフトウェアの目的・利用者価値・文書・コード・実行時の証拠を結び付け、
現状理解、追加調査、改善案の比較と人間の判断を支援する製品です。この説明と以降の条件を、
評価素材の設計に必要な前提としてください。過去の会話や暗黙のローカルファイルを前提にしません。
ここに挙げる体験は評価目標であり、現行版での実装を保証する一覧ではありません。

以下の三つを区別してください。
- 評価される製品：probe-agent。
- probe-agentに理解・観測させる架空の対象：こもれびヘルプデスク。
- 今あなたが作業しているフォルダ・プロジェクト：生成作業の場所。上の二つの実装とは限らない。

用語の意味：snapshotは固定した版の証拠集合、traceは実行時の記録、probe pointは観測を置く箇所、
canonicalは人が確認して正本にした理解、oracleは評価者だけが持つ判定基準です。
Interviewは意図や不明点を確認する対話、Assistantは画面・対象の文脈に沿った相談を指します。
Replayは固定入力での再実行、Experimentは基準実装と候補の比較です。
これらは概念の説明であり、実在する画面名・API名を指定するものではありません。

standaloneでは、この指示文と明示的に渡された入力だけを題材・製品知識として使います。
ホスト環境の作業規則には従いつつ、実行先プロジェクト固有の仕様・コード・業務情報を
架空データへ混入させないでください。probe-agentのcheckout、AGENTS.md、CLAUDE.md、docs/を
別の場所から探すことや、外部サイトの調査は必要ありません。
product-awareではprobe_agent_sourceとreference_materialsに明示された範囲だけを追加で参照し、
資料の版・出典を記録してください。記述された仕様と実装で確認できた機能は分けてください。
参照元が未指定・読めない場合はその事実を報告し、素材生成はstandaloneの範囲で進めます。
実行先の別リポジトリを代わりに使ったり、パスやAPIを推測したりしないでください。

ファイル作成時は出力先を解決して冒頭に明示し、生成物をoutput_dir内にまとめてください。
既存の同名ファイルを上書きせず、初回の衝突時は別名の新規出力先を使って報告してください。
指定先が書き込み不能なら、ファイル名付きの内容を回答として出力できます。
生成物内のファイル参照はデータセットルート基準の相対パスに統一し、その基準をmanifestに記録します。
実行手順には作業ディレクトリを明記し、移動前の絶対パスを生成物の必須参照にしないでください。
この指示文や製品資料への参照は、生成物を読むための必須条件にしないでください。

S1以降では、指定した前段階のmanifestと関連する資料・ケース・IDを読めることを確認してください。
不足がある場合は必要な入力を列挙し、その入力に依存する差分生成を保留してください。
前段階の内容を推測で補完したり、S0を再生成して継続扱いしたりしないでください。
継続時は前段階を保持して新段階のファイルを追加し、既存manifestも履歴として保存してください。

seedは生成条件の識別子です。同じseedによるLLMの再生成が同じデータになるとは主張しません。
比較には保存済み生成物を使い、生成モデル、指示文の版、ファイルのhashを記録してください。
hashやcommitは実際に計算・確認できたものだけを記載し、それ以外は未確認としてください。

【1. 評価する体験】
次の流れを評価できる素材にしてください。
1. 利用者が「今、何を判断したいか」を自分の言葉で伝える。
2. probe-agentが目的・利用者価値・現状・根拠・不明点を整理する。
3. コードや資料で分かることを調べ、人にしか決められないことを質問する。
4. 小さく実行できる次の一手と、必要な場合に限った観測案を提示する。
5. 新しい証拠で助言を更新し、不要になった観測を縮小・終了する。
6. 採用・適用・観測開始・達成確認などは、製品の人間による判断境界を維持する。

目的→利用者の困りごと→目標→業務の流れ→要件→機能→実装→観測→判断が追えるようにします。
ただし、最初から全項目を完成させないでください。未決定や未観測も正式なデータです。
提案された機能と実装済み機能を分け、仕様だけから「実装済み」と判断しないでください。

【2. 共通プロジェクト】
架空名は「こもれびヘルプデスク」。問い合わせを受け付け、カテゴリから担当へ振り分け、
受付結果を返すPythonの小さなツールです。外部サービスはローカルの代替実装で表現します。
最初は1チーム、利用者約10人、問い合わせ約20件/週、開発保守は兼務の1人です。
これらは設定値であり、実測値ではありません。週次負荷と少数の試験入力は別に扱います。
最初の目的は「担当不明の問い合わせを減らすこと」。高速化や完全自動化を最初から目的にしません。
分類方式は単純な決定的ルールで十分です。大規模な構成やLLM接続を初期条件にしないでください。

【3. ペルソナは二つの立場を分ける】
S0では各立場2人、計4人までにしてください。氏名は架空、連絡先が必要ならexample.comを使います。
A. probe-agentを操作し、助言を受けて判断する人
   - 兼務開発者：Pythonは読めるが業務知識は不完全。今回の評価作業に使える時間は20分。
   - 業務責任者：業務ルールと優先順位を決められるが、コードの詳細は説明できない。
B. 対象サービスを利用し、価値や不便を受ける人
   - 問い合わせを出す社員：カテゴリを正確に選べず、受付されたか不安になる。
   - 問い合わせを受ける担当者：担当外の依頼と手動での付け替えが負担になっている。

各人について、役割、達成したいこと、困る場面、知っている事実、知らないこと、誤解、
判断権限、時間制約、技術習熟度、成功と感じる条件、実際に言いそうな発言を記載してください。
担当者の役割と実際の製品アカウント権限は分け、権限設定は投入前の確認項目にしてください。
性格・年齢などの装飾を増やさず、回答や操作判断が変わる属性を優先してください。

操作者には会話用ロールカードも作ってください。質問された範囲だけ答え、知らないことは
「分からない」と答え、提示されていないコード・将来段階・評価者の正解を参照しない台本にします。
業務責任者の意図を、開発者が確定事項として代弁する台本にしないでください。

【4. 段階的な成長】
全段階は下表の概略だけを示し、詳細な生成は指定されたstageだけに限定してください。
件数は架空の業務規模です。投入データ件数・性能試験の実行件数は別途明記してください。

S0：小規模導入
- 1チーム、約10人、約20件/週。主要機能3つ、主要な利用の流れ1つ、未決事項1つ。
- 正常系、情報不足、文書と実装の食い違いを個別に確認する。
- 観測は最大2点を初期案の上限とする。資料確認だけで済む課題も必ず入れる。

S1：利用拡大
- 3チーム、約50人、約200件/週。カテゴリと例外ルールが増える。
- 担当の付け替えと、失敗が記録されていない偏った観測データを加える。
- 件数が多い箇所だけを重要と判断しないか、観測の偏りを指摘できるかを見る。

S2：構成の複雑化
- 約200人、約1,000件/週。通知を模した処理、待ち行列、再試行を追加する。
- 同じ遅延症状について、待ち時間・処理時間・再試行の少なくとも2つの競合仮説を作る。
- 初期証拠だけでは断定できず、追加観測で仮説を区別できるようにする。

S3：観測の見直し
- 約500人、約5,000件/週。定常的な大量処理、低頻度で重大な誤振り分けを共存させる。
- 重複ログ、機微な自由文、保持費用、不要になった観測点を含める。
- 低頻度の重大事象を見落とさず、観測量・項目・保持期間を減らせるかを見る。
- 実際の機密情報は使わず、架空の「保存不要な自由文」として扱う。

S4：目的・体制の変更
- 利用量はS3程度のまま、専門チームへの引き継ぎとサービス目標の変更を入れる。
- 「受付速度」より「適切な担当への到達」を重視する明示的な判断を追加する。
- 古い資料・過去の採用理由・変更後の意図を残し、古い助言を再評価できるかを見る。
- 役割の引き継ぎ、過去の会話の再開、改訂前の前提を使った提案を確認する。

段階ごとに主要な変化は2つまで。大きな障害を一度に混ぜず、原因を比較可能にしてください。
S1以降でも機能を増やすだけにせず、何もしない・追加確認・既存設定の変更・観測終了を
妥当な判断として含めてください。継続時は固定IDを維持し、変更・追加・廃止・訂正を区別します。

【5. 初回S0の生成量】
- プロジェクト概要：800〜1,200字程度。
- ペルソナ：4人、各200〜350字程度。ロールカードは別途簡潔に。
- 資料：短いREADME、業務ルール、現時点の要望。最初から詳細仕様書一式を作らない。
- 主要機能：受付・振り分け・受付結果生成の3つ。目標は1つ、受入基準は2〜3個。
- 入出力例：合計12件以内。正常・未知カテゴリ・欠損入力を含む。
- 評価ケース：以下の3件。1件ごとに初期状態へ戻して実施できるようにする。
  C01 正常系：「何ができるツールで、最初に何を確認すればよいですか？」
  C02 情報不足：「これで問い合わせのたらい回しは減りますか？」
      受付成功の証拠はあるが、担当変更回数や利用者の結果は未観測とする。
  C03 矛盾：「READMEでは総務に届くはずなのに、未割当になりました。なぜですか？」
      READMEと実装・実行例のどちらかに更新漏れを設け、意図した挙動は業務責任者に確認できる。

C01を基準に、C02/C03は必要な差分だけを適用する独立した枝にしてください。
C03の矛盾をC01に混入させないでください。矛盾箇所の正解ラベルは評価者用にのみ置きます。
documentsモードでは、実装が根拠になる箇所だけ短いコード抜粋を含めます。
例示の入出力・ログを実際の実行結果と表現してはいけません。

【6. 公開する情報と評価用の情報を分ける】
生成物は次の構成にしてください。MarkdownとJSONを基本とし、JSONは構文的に有効にします。
ファイルを作れる場合はファイルへ、作れない場合はファイル名付きの完全な内容を出力します。
下のdataset/はoutput_dir自体を表す説明用の名前です。S0は指定したstageに読み替えます。

dataset/
  manifest.json                  # 版、段階、条件、生成物一覧、来歴、件数
  public/S0/                     # probe-agentが現在参照してよい資料だけ
    project.md
    stakeholders.md              # 対象サービスの利用者像・公開済みの役割情報
    materials/                  # README、業務ルール、要望、必要なコード抜粋
    samples.json                # 少数の入出力例。syntheticを明記
  operator/S0/
    personas.md                 # probe-agent操作者の事情・知識・判断権限
    role-cards.md               # 質問への応答台本。初期投入資料には含めない
    runbook.md                  # ケース別の投入・操作・開示・初期化手順
  evaluator/S0/
    oracle.json                 # 隠れた事情、期待する判断、禁止する断定
    observation-options.json    # 観測候補、費用、区別できる仮説、終了条件
    scorecard.md                # 実測前の評価表。結果欄は未測定
  changes/S0.md                  # 初期設定。以後は前段階からの差分

executableモードではpublicの指定段階内に小さなtarget-repo/を追加し、実装・入力・テストを置きます。
operator、evaluator、将来段階の資料は対象repository・snapshot・検索対象から物理的に外します。
データセット全体や生成作業先の親プロジェクトを、probe-agentへ取り込むrepositoryに指定しないでください。
ファイル名やコメントに「ここがバグ」「正解」といった答えを埋め込まないでください。
同一会話でoracleを見たAIを、そのまま盲検評価の回答者にしないでください。

各証拠には安定したID、版、出典、記録時点、開示条件を付けてください。
事実の状態（確認済み／主張／仮説／不明／矛盾）と、取得状態（取得済み／未取得／取得不能）を
分けてください。これらは評価素材のメタデータであり、製品のAPI enumと同一とは限りません。
未来の証拠、操作者だけが知る事情、評価者だけが知る原因を初期資料へ混ぜないでください。
単に取得できなかった情報を「存在しない」という設定に変えないでください。

【7. ケースの投入台本とoracle】
各ケースを固定IDで対応付け、以下を記載してください。
- 初期状態、使うペルソナ、今回判断したいこと、利用者の最初の発言。
- 初期開示する資料・コード・観測結果のID。非開示情報と開示条件。
- probe-agentで行う操作の意味と、利用可能なら実在を確認した画面・APIへの対応。
- 同じケースでの追質問、提示する追加証拠、利用者の訂正を必要な範囲で記載。
- 許容する判断・質問・次の行動、根拠ID、不確実性、してはいけない断定。
- 完了条件、途中で失敗した際の再開条件、終了後の初期化・差分の戻し方。

唯一の正解文章は作らず、「満たすべき判断条件」で評価してください。
非公開の原因を言い当てることではなく、公開済みの証拠で言える範囲と、必要な追加調査を評価します。
追加証拠は選択した観測で得られるものだけを開示します。同じ観測には同じ結果を返します。
未実装の観測方法を選んだ場合は、結果を得たことにせず「提案のみ／実行未対応」とします。

各手順には capability_status = verified / unverified / unsupported を付け、確認根拠を記載します。
製品コードを読めない場合はunverifiedとし、存在しないURL・API・自動インポート機能を作らないでください。
unsupportedの機能は将来の受入基準として残し、現在の動作確認ではblockedとして分離します。

【8. 助言と観測の最適化を評価できる仕掛け】
各段階の主要な判断について、観測候補を最大3つ作ってください。
候補ごとに、判断したい問い、競合仮説、観測点・項目、期間または標本数、
サンプリング、概算の件数・データ量・導入工数・実行負荷、保存しない情報、
得られる証拠と得られない証拠、停止・縮小条件を明記してください。
数値は単位・計算方法・分母を付け、設定上の見積もりと実測値を区別してください。

次の候補を比較できるようにします。
- 判断に十分な最小の観測（または資料確認だけで済み、追加観測が不要な選択）。
- 同じ判断はできるが、過剰に多い情報や自由文を集める観測。
- 安価だが、競合仮説や低頻度の重大事象を区別できない観測。

予算・制約をケース開始前に固定してください。S0は観測点最大2つ、操作者の作業20分を目安とし、
費用・保存容量など他の上限は必要になった段階で具体化します。上限の緩和は判断事項にします。
S2以降は、同じ公開済み症状に異なる原因を持つ対照ケースを最低1組作ってください。
単に前の段階の答えを繰り返す助言では合格できず、追加証拠で判断を変えられるようにします。
S3では少なくとも1つ、過去に役立った観測の継続価値が下がり、終了または縮小が妥当な例を作ります。

評価者用に、利用可能な候補の範囲で判断条件を満たす最小費用案を示してください。
数学的な全体最適を主張せず、費用と見逃しのトレードオフを残してください。
助言が良いことと、製品がその設定を実際に保存・実行できることは別に採点します。

【9. executableモードの追加条件】
- S0はPython実装3ファイル以内・実装約200行以内を目安にし、少数のテストと実行手順を付ける。
- 固定入力と固定乱数で再実行でき、外部API・メール・有料サービス・実認証情報を必要としない。
- 業務ルール、コード、テスト、例示データの整合を確認し、意図的な矛盾はケース差分へ分離する。
- 不具合の現状再現テストと、望ましい仕様を示す未達テストを区別する。
- probe-agentのSDK・schemaを利用できる場合は実物に従い、存在しない引数やフィールドを作らない。
- SDK・schemaを参照できない場合も、Python標準ライブラリで動く架空ツールと単体テストは生成する。
  製品への送信処理・SDK接続は未接続として残し、独自形式のログをprobe-agent互換と呼ばない。
- committed-files-onlyのsnapshotに対応するため、投入前に対象のcommitを固定する手順を用意する。
  作成・確認していないcommit SHAは発行しない。評価者用ファイルは対象repoへcommitしない。
- 合成ログと、生成したコードを実行して取得したtraceを分ける。性能をsleepで模擬する場合も明記する。
- 実行できなかった確認は未実施とし、「動作確認済み」と報告しない。

【10. 採点表】
次を個別に記録し、総合点だけで合否を決めないでください。
1. 操作UX：課題完了の可否、次の操作を見つけるまでの時間、操作数、迷い・手戻り、再開の可否。
2. 回答品質：直接性、事実の正確さ、根拠との整合、不確実性の扱い、会話の連続性を各0〜2。
3. 助言の適合：目的・ペルソナ・成長段階・制約に適合するか。過剰な設計や不要な質問の件数。
4. 観測の有用性：区別すべき仮説を区別したか、重大事象を見逃したか、判断までの追加観測回数。
5. 観測の負担：観測点数・イベント数・バイト数・導入時間・処理負荷、縮小・終了の妥当性。
6. 来歴と境界：過去の判断を辿れるか、古い根拠を識別するか、提案と適用を混同していないか。

回答品質の0は不成立、1は一部成立、2は十分成立とし、ケースごとの判定例を付けてください。
重大な誤断定、非公開情報の混入、無承認の適用、未観測を成功扱いすることは件数を別記します。
未実施・未対応・未測定は0点や成功へ変換しません。合成値で実測欄を埋めないでください。
各評価には実回答・操作記録・証拠IDを付けられる空欄を設けます。

比較条件として、データ版、製品commit、モデル・設定、ケース順序、反復数、初期状態を記録します。
初回は3ケースを各1回の探索的確認とし、少数の結果から統計的な品質保証を主張しないでください。
製品の改修前後では同じデータを使い、段階比較では同じ製品版を使います。
自動台本による動作確認、実LLMの助言評価、人が操作するUX評価を分離してください。
ペルソナAIによる操作はUX上の仮説を発見する用途とし、代表利用者の実測結果とは扱いません。

【11. 出力順と自己点検】
最初に、今回作る範囲・使い方・ファイル一覧を短く示し、指定段階のデータを出力してください。
続いて評価者専用資料を明確に分離し、最後に以下の点検結果と未確認事項を示してください。
- ID・参照・版・時系列が一致するか。段階間で同じ対象のIDを変えていないか。
- 意図的な矛盾以外で、資料・コード・データ・oracleに矛盾がないか。
- 各ケースは公開した証拠で評価可能か。隠れた正解を知らないと合格できない条件になっていないか。
- 小規模な段階に後の複雑さを持ち込んでいないか。初期化と独立実行が可能か。
- 機能の実装状態・合成データ・実行結果・未測定を分けているか。
生成したケースは検証候補です。データ生成だけでprobe-agentの評価に合格したとは報告しないでください。
````

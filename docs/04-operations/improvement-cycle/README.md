# 製品状態から選ぶ改善サイクル

[docs目次](../../README.md) · [課題ナレッジ](../../02-challenges-and-decisions/issue-knowledge/README.md)

**役割:** guide-or-runbook。**状態:** current（リポジトリ開発の文書運用）。**確認時点:** 2026-09-19。
**上位方針:** [Vision](../../00-product/vision-and-core-requirements.md)。
[記事](https://zenn.dev/dx_junkyard/articles/88658ed7a7231d)の「状態と利用見通しから改善対象・方法を選ぶ」考え方を適用する。

この手順はprobe-agent自身を開発する際に使う。製品の自動推定・Recipe選択APIを実装済みとはしない。
製品内の [Evolutionary Pipeline](../../01-specifications/capabilities/evolutionary-pipeline.md) は対象システムの
改善機能の契約、[AI Agent Improvement Guide](../ai-agent-improvement-guide.md) は観測・shadow比較の手順を所有する。
ここでは、それらをいつ使うかを含む開発の判断と結果を記録する。

```text
目的・根拠付き状態 + 利用シナリオ
  → 改善候補の比較 → 過去の型・Recipeを照合
  → 発見 → 選別 → 設計 → 実装 → 検証 → 是正 → 記録
  → 状態・原因・Recipeの条件・選択理由を更新 → 次の判断
```

## 1. 最初に作る着手の地図

[計画テンプレート](PLAN_TEMPLATE.md)を `docs/02-challenges-and-decisions/improvement-plans/` へコピーする。
[導入時の例](../../02-challenges-and-decisions/improvement-plans/2026-09-19-knowledge-bootstrap.md)は未実測を明示した使い方の例。
対象版、目的、現在状態、想定利用、候補、採用理由、検証条件、予算、停止条件を先に揃える。
過去の監査の問題を現行版でも再現すると仮定しない。

## 2. 各段の入力と出口

| 段 | 実施内容 | 次へ渡す証拠 |
| --- | --- | --- |
| 発見 | 状態を観測し、辞書の問い・境界追跡・実データで原因候補を探す | 対象版、再現、根拠、未観測。原因不明なら調査を候補にする |
| 選別 | 目的・利用見通し・影響・費用・依存・不確かさから候補とRecipeを比較 | 採用案・見送り案・理由、既存の承認範囲 |
| 設計 | 正本の契約、不変条件、状態遷移、受入条件を定める | 期待挙動、失敗条件、検証と復旧方法 |
| 実装 | 計画の境界で実装する。必要な契約を同時更新 | 差分、関連仕様、実装上の制約 |
| 検証 | Recipeの条件で期待・実測を比較する | コマンド・環境・対象版・結果・未確認を含む検証記録 |
| 是正 | 原因と受入条件へ戻って不一致を直し、必要範囲を再検証 | 未解決事項と停止・保留理由。合格するまで闇雲に反復しない |
| 記録 | 状態、課題型、Recipeの有効条件・見逃し、選択理由を更新 | 次の観測条件・再開条件と各正本へのリンク |

文書だけの変更や調査だけの改善でも使える。不要な段は理由付きで「対象外」とし、実行したとは書かない。

## 3. 改善対象とRecipeの選び方

状態は [state-assessment.md](state-assessment.md) の8性質で記録する。原因の4軸とは分ける。
状態が悪い項目や件数が多い型を機械的に優先しない。最低2案（現状維持・調査・縮小も可）を並べ、
次を文章で比較する。

- 目的への寄与と、現在・近い将来の利用条件で必要になる理由。
- 放置時の影響、実装・検証・運用の負担、先に必要な変更。
- 原因と効果の不確かさ、追加観測で判断を変えられるか。

利用シナリオ（例: 複数人が同じSystemを扱う）と効果仮説（版を固定すれば混在を防げる）は別欄にする。
想定を事実へ昇格しない。Recipeは適用条件・非適用条件・過去の見逃しを見て選び、今回の条件を補う。

| 今回の変更・状態 | 最初に読むもの |
| --- | --- |
| revision、再生成、同時操作、候補の適用 | [境界・版のRecipe](recipes/boundary-and-version.md)、辞書のversion-lineage |
| 画面間の反映・保存・復帰、未表示フォーム | [利用導線のRecipe](recipes/user-journey.md)、辞書のdelivery-path |
| 生成値・表示語・API契約 | 辞書のcontract-transfer、境界Recipe |
| 利用者価値が未実測、部品テストのみ成功 | 辞書のacceptance-evidence、利用導線Recipe |
| 関数の候補品質・速度・例外 | [既存の観測・shadow比較手順](../ai-agent-improvement-guide.md) |

## 4. 実行の境界と止め方

計画に対象範囲、外部呼出し・時間・費用の上限、データの扱い、停止条件を記す。
権限不足、重要な前提の変化、予算到達、期待と逆の結果があれば止め、原因・再開条件を残す。
AIは調査・比較・実装・分類候補を担当できる。価値・リスク受容・委譲範囲はユーザーの既存指示を根拠にする。
毎回の形式的な再承認は求めず、既に委譲された範囲では進める。製品のmanual gateを文書運用で緩めない。

## 5. 結果を次の選択へ返す

[結果テンプレート](RESULT_TEMPLATE.md)を `docs/03-validation/improvement-cycle/` に置く。
採用した仮説が支持されたか、目的の状態が変わったか、未観測は何かを記す。
成功はテスト合格だけで判定せず、計画の受入条件と観測範囲で判断する。

Recipeはcandidateから始める。独立した2回以上の適用結果（適用版・条件・実測・費用・後発の見逃し）を
比較し、人が有効条件と非適用条件を確認したらreusableへ変更する。適用回数だけで自動昇格しない。
失敗・逆効果・適用不能も結果としてリンクする。内容を変える際は版を上げ、過去結果が参照した版を残す。
今回追加したRecipeは過去監査から抽出した候補で、Recipeとして実行・成功した履歴はまだない。

振り返りで同型再発・見逃し・検証経路不足・段の省略が判明したら、結果記録をsourcesとして
課題ナレッジにcycle層のエントリを追加する。症状の場所ではなく原因で分類する。
次の巡回では索引の未確定分類・仮説・提案、Recipeの見逃し、状態の未観測範囲を見る。
件数・発見観点の偏りは点検の入口であり、件数増減を品質の目標にしない。

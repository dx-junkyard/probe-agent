自律改善が難しい・行き詰まったと判断したとき、状況と保持条件から必要な候補を探す。
通常の作業に一律照合を要求しない。担当エージェントが実適用・効果検証・改訂を行い、人の確認を待たない。
すべてcandidateで、独立した適用効果は未確認。以下は手動の入口であり、IKの生成索引とは別に管理する。

| ID / 版 | 抽象課題と解決原理 | 最初に確認する状況 |
| --- | --- | --- |

| [EC-LP-0002 / v1](EC-LP-0002-fixed-information-v1.md) | 固定情報の意味を後続操作から守る | 過去の前提・固定版・完了証拠を後から参照する |

## 選択と記録

1. 小さい試行は既存記録へ、複雑な試行は[計画雛形](../../../docs/04-operations/improvement-cycle/PLAN_TEMPLATE.md)で状況・保持条件・対象版を定める。
2. 候補を「適合候補／要観測／非適合」で照合する。座標の一致だけで選ばず、理由を記す。
3. 候補の版と派生形IDを固定し、補完する対策の組合せ、見送る対策、固有の検証を選ぶ。
4. 対象の契約を確認して具体策を設計する。事例の実装をそのまま移植しない。
5. [結果雛形](../../../docs/04-operations/improvement-cycle/RESULT_TEMPLATE.md)へ実測を残す。
   候補の「適用実績」から結果記録へリンクし、後発の見逃しも追記する。

両候補の保持条件がある場合は併用する。該当しなければ従来の辞書・EC-P・Recipeへ戻る。
候補を照合して見送った場合だけ理由を短く記録する。参照自体が不要な案件に不使用記録は要求しない。

## 追加・改訂・確認

新規候補は[配布元のpattern雛形](../../../vendor/evolution-controller-0.1.0-preview.1/templates/pattern.md)と
既存2候補を参考にする。内容の必須項目、成熟条件、版の保持は上記運用契約に従う。
IDは既存最大+1、欠番は再利用しない。本文の適用条件・解決原理・派生形・検証を変えるときは
`-v2.md`等を新設し、入口を切り替える。旧版と使用結果を残す。
実績・後発指摘の追記は日付付きで同じ版へ記録できるが、過去の結論を上書きしない。

初期導入の[整合確認と非適用例](../../../docs/03-validation/improvement-cycle/2026-09-27-knowledge-abstraction.md)を
更新時の確認観点に使う。リンク、ID・版、根拠IKの実在、補完と派生の区別、
同一系譜の扱いを確認し、既存の`issue_knowledge.py --check`も実行する。
同検査器はこの層の意味や成熟を検査しない。`knowledge_links.py`で相対ファイルリンクを確認し、意味と効果は実適用で確認する。
専用の機械可読スキーマ・自動推薦は効果確認後に検討する。
